## ADR-001

### 체결은 자체 엔진이 판정한다

**맥락** — "구매까지 할 수 있다"를 구현하는 방법이 두 가지다. 증권사 주문 API로 전달하거나,
우리가 직접 체결을 판정하거나.

**결정** — 자체 체결 엔진(모의 거래). 시세만 외부에서 실시간으로 받는다.

**근거** — 학습 목표 네 개 중 가장 어려운 것이 동시성인데, **동시성 문제는 잔고와 주문 상태를
우리가 소유할 때만 발생한다.** 증권사 프록시 방식을 택하면 잔고 검증·주문 상태 전이·체결
반영이 모두 증권사 서버 안에서 일어나고, 우리 쪽에는 HTTP 호출과 응답 매핑만 남는다. C1(예수금
이중 차감)이나 C2(취소와 체결의 경쟁)를 겪을 기회 자체가 사라진다.

**배제한 대안** — 증권사 주문 API 프록시. 외부 장애 대응 학습에는 더 좋지만, 그 목표는 시세
파이프라인(§07 R1~R3)만으로도 충분히 달성된다. 계좌 개설이 필요하다는 부담도 있다.

**결과** — 오더북·체결 규칙·원장을 직접 구현해야 하므로 Phase 3의 분량이 크게 늘어난다. 이건
비용이 아니라 목표다.

**재고 시점** — 실제 자금으로 거래하고 싶어질 때. 그때는 체결 엔진을 버리는 것이 아니라
`ExecutionGateway` 인터페이스의 구현을 하나 더 붙이는 형태가 된다.

## ADR-002

### 체결 상대방은 가상 유동성 공급자

**맥락** — 자체 체결 엔진을 만들면 "누구와 체결하는가"를 정해야 한다.

**결정** — 외부 실시간 시세를 기준으로 즉시 체결을 판정하는 가상 상대방을 둔다. 사용자 간
매칭도 가능하도록 오더북은 그대로 유지한다.

**근거** — 사용자 간 매칭만 구현하면 **혼자 테스트할 때 주문이 영원히 체결되지 않는다.** 체결이
일어나지 않으면 원장·포지션·평균단가·체결 알림을 검증할 방법이 없고, Phase 3~4가 통째로
막힌다. 가상 상대방을 두면 가격-시간 우선 오더북 로직은 그대로 배우면서 체결이 실제로 발생한다.

**배제한 대안** — 사용자 간 매칭 전용. 이론적으로 더 "진짜"지만 검증 불가능한 시스템은 학습
가치가 없다.

**결과** — `execution.counter_order_id`가 nullable이다. NULL이면 가상 상대방과의 체결이다.
체결 가격은 시세가 `stale`일 때 신뢰할 수 없으므로, 그 상태에서는 시장가 주문을 거부한다(§R1).

**재고 시점** — 실제 사용자가 여러 명 붙어 오더북에 물량이 쌓이기 시작할 때. 가상 공급자를
"오더북에 유동성이 없을 때만" 동작하게 축소할 수 있다.

## ADR-003

### Spring MVC + 가상 스레드 (WebFlux 아님)

**맥락** — 초당 수천 건의 시세를 받아 다수 클라이언트에 밀어야 한다. 전통적으로는 WebFlux를
떠올리는 요구사항이다.

**결정** — Spring MVC를 쓰고 `spring.threads.virtual.enabled=true`로 가상 스레드를 켠다.

**근거** — 학습 목표는 **락과 트랜잭션의 이해**다. WebFlux는 `Mono`/`Flux` 체인 때문에 "어디서
락이 잡히고 어디서 트랜잭션 경계가 끝나는지"를 읽기 어렵게 만든다. `@Transactional`이 리액티브
체인에서 어떻게 동작하는지 자체가 별도의 난제이고, 그 난제는 이 프로젝트가 배우려는 것이
아니다. Java 21의 가상 스레드는 블로킹 코드를 그대로 유지하면서 스레드당 메모리 비용을 없애므로,
코드 가독성을 잃지 않고 확장성만 얻는다.

**배제한 대안**
- **WebFlux** — 위 이유. 그리고 JDBC는 블로킹이므로 R2DBC로 갈아타야 하는데, R2DBC는
  `RETURNING` 절과 배치 처리에서 JDBC보다 제약이 많다.
- **플랫폼 스레드만** — SSE 커넥션 하나당 스레드 하나면 동시 구독자 수가 수천 명에서 막힌다.

**결과** — 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 캐리어 스레드를 고정(pinning)한다.
그래서 락이 필요한 곳에서는 `synchronized` 대신 `ReentrantLock`을 쓴다. 이건 Phase 3에서 실제로
주의해야 할 지점이다.

**재고 시점** — 시세 팬아웃이 가상 스레드로도 한계에 부딪힐 때. 그때는 SSE 푸시 경로만
리액티브로 분리하고 주문 경로는 MVC로 남기는 하이브리드가 가능하다.

## ADR-004

### JPA를 쓰지 않고 `JdbcClient`로 SQL을 직접 쓴다

**맥락** — Kotlin + Spring Boot의 기본 선택은 Spring Data JPA다.

**결정** — JPA와 Hibernate를 쓰지 않는다. `JdbcClient`로 SQL을 직접 작성한다.

**근거** — 이 프로젝트에서 가장 중요한 기법이 **조건부 원자적 UPDATE + `affected rows` 확인**이다.

```sql
UPDATE account
   SET available_cash = available_cash - :amount
 WHERE id = :id AND available_cash >= :amount;
-- affected rows == 0 → 잔고 부족
```

문제는 JPA의 가장 자연스러운 사용법이 정확히 C1이 터지는 코드라는 점이다.

```kotlin
val account = repository.findById(id)     // SELECT
account.availableCash -= amount           // 애플리케이션에서 계산 ← 여기가 틈
repository.save(account)                  // UPDATE
```

JPA로도 `@Query`에 네이티브 SQL을 넣어 조건부 UPDATE를 할 수 있지만, 그러면 영속성 컨텍스트와
DB 상태가 어긋나 `clearAutomatically`, `flushAutomatically` 같은 옵션을 계속 신경 써야 한다.
프레임워크와 싸우는 시간이 배우는 시간을 잡아먹는다.

**배제한 대안**
- **Spring Data JPA** — 위 이유.
- **jOOQ** — 타입 안전한 SQL로 훌륭한 선택이지만 코드 생성 단계가 Phase 0을 무겁게 한다.
  쿼리가 복잡해지면 재고할 가치가 있다.
- **Exposed** — Kotlin 친화적이지만 Spring 트랜잭션 통합이 JDBC만큼 매끄럽지 않다.

**결과** — SQL 문자열을 직접 관리해야 하므로 타이포가 런타임에 발견된다. Testcontainers 통합
테스트가 이를 잡는 안전망이다(ADR-013). 읽기 전용 조회가 늘어나면 JPA를 읽기 모델에만
추가하는 선택지가 남아 있다.

**재고 시점** — 조회 쿼리가 30개를 넘어 문자열 관리 비용이 커질 때 → jOOQ.

## ADR-005

### 모듈러 모놀리스 + 도메인 순수성을 빌드로 강제

**맥락** — 6개 모듈로 나눌지, 단일 모듈로 시작할지, 처음부터 마이크로서비스로 갈지.

**결정** — Gradle 멀티모듈 모놀리스. `core-domain`은 프레임워크에 의존하지 않으며, 이를
`checkDomainPurity` Gradle 태스크가 강제한다.

**근거** — 두 부분으로 나뉜다.

*마이크로서비스를 안 하는 이유*: 주문 접수 → 예수금 예약 → 체결 → 원장 기록이 **하나의
트랜잭션**이어야 한다(INV-4). 서비스로 쪼개면 이것이 분산 트랜잭션 문제가 되고, Saga·보상
트랜잭션이라는 별개의 난제가 동시성 학습을 가려버린다. 그리고 아직 경계가 어디인지 모른다.

*모듈로 나누는 이유*: 단일 모듈이면 `core-domain`에 Spring을 쓰는 것을 막을 방법이 없다. 그런데
§12의 속성 기반 테스트(무작위 주문 수만 건으로 불변식 검증)는 도메인 로직이 Spring 컨텍스트
없이 밀리초 단위로 실행될 때만 현실적이다. 모듈 경계가 그 실행 속도를 지키는 장치다.

*빌드로 강제하는 이유*: 규칙을 문서에만 적으면 언젠가 누가 편의를 위해 Spring 의존성을 하나
추가한다. 그 시점을 사람이 코드 리뷰로 잡아내길 기대하지 않는다.

```
core-domain 순수성 위반 (§04) — 프레임워크 의존성이 발견되었습니다:
  - org.springframework:spring-context:6.2.8
  - io.micrometer:micrometer-observation:1.14.8   ← 추이적 의존성까지 잡는다
```

**배제한 대안** — 단일 모듈 + 패키지 규칙(ArchUnit). ArchUnit도 좋은 도구지만 클래스 참조를
검사할 뿐, classpath에 무엇이 있는지는 막지 못한다. 무거운 라이브러리가 테스트 실행 시간에
영향을 주는 것이 문제이므로 classpath 수준에서 막아야 한다.

**재고 시점** — 배포 단위를 실제로 분리해야 할 때(시세 수집기만 따로 스케일링). 그때는 모듈
경계가 이미 그려져 있으므로 분리 비용이 낮다. 이것이 모듈러 모놀리스의 목적이다.

## ADR-006

### 금액은 최소 단위 정수로만 보관한다

**맥락** — 금액을 `Double`, `BigDecimal`, `Long` 중 무엇으로 표현할지.

**결정** — `Money` 값 객체를 만들고 내부는 최소 단위 정수(`Long`)로만 보관한다. KRW는 원, USD는
센트. `BigDecimal`은 입출력 변환에만 쓴다.

**근거**
- `Double`은 `0.1 + 0.2 != 0.3`이다. 논쟁의 여지가 없다.
- `BigDecimal`을 내부 표현으로 쓰면 scale이 다른 값이 섞이면서 `equals`와 `compareTo`가
  갈라진다 — `BigDecimal("1.0") != BigDecimal("1.00")`인데 `compareTo`는 0을 반환한다. 잔고
  비교에서 이 불일치는 찾기 어려운 버그를 만든다.
- 정수 하나면 등가성·비교·해시가 전부 일관되고, DB의 `BIGINT` 컬럼과 1:1로 대응된다. ADR-008의
  원자적 덧셈도 정수여야 가능하다.

**결과** — 두 가지를 조용히 넘기지 않고 예외로 실패시킨다.
- 오버플로: `Math.addExact` 사용. 잔고가 음수로 감싸면 INV-1이 애플리케이션 레벨에서 무의미해진다.
- 소수점 손실: `RoundingMode.UNNECESSARY`. 0.5원을 0원이나 1원으로 만들면 원장 합계(INV-2)가
  어긋나고 원인 추적이 거의 불가능하다.

**재고 시점** — 없음. 이건 되돌릴 결정이 아니다. 다만 통화 추가(§13) 시 `Currency` enum에
항목이 늘어나며, 그때 `Money`의 산술 코드가 한 줄도 바뀌지 않아야 한다. 바뀐다면 추상화가
틀렸다는 신호다.

## ADR-007

### 원장은 append-only, 잔고 컬럼은 캐시

**맥락** — 예수금을 `account.available_cash` 컬럼만으로 관리할지, 원장(ledger)을 따로 둘지.

**결정** — 모든 금액 변동을 `ledger`에 한 줄씩 append하고, `account`의 잔고 컬럼은 빠른 조회를
위한 캐시로 취급한다. 원장의 UPDATE·DELETE는 **트리거로 차단**한다.

**근거** — 잔고 컬럼만 있으면 "지금 얼마인가"는 알 수 있지만 **"어떻게 이 값이 되었나"를 알 수
없다.** 동시성 버그로 80만원이 공짜로 생겼을 때, 잔고만 보면 언제 어디서 생겼는지 추적할
방법이 전혀 없다. 실제 금융 시스템이 복식부기를 쓰는 이유가 이것이다.

트리거로 막는 이유는 ADR-005와 같다. "원장은 수정하지 않는다"를 문서에만 적으면 언젠가 데이터를
고치려는 UPDATE가 실행된다.

```sql
CREATE TRIGGER ledger_append_only
    BEFORE UPDATE OR DELETE ON ledger
    FOR EACH ROW EXECUTE FUNCTION ledger_reject_mutation();
```

**결과** — 잔고 컬럼과 원장 합계가 어긋날 수 있다(INV-2). 그래서 `v_account_ledger_consistency`
뷰를 만들어 `drift`를 SQL 한 번으로 확인하고, Phase 6에서 이를 최고 우선순위 알람으로 건다.

**배제한 대안** — 이벤트 소싱(잔고 컬럼 없이 원장만). 조회할 때마다 전체 원장을 접어야 하므로
주문 검증 지연이 원장 크기에 비례해 늘어난다. 잔고 스냅샷 + 원장이 실용적 타협점이다.

**재고 시점** — 없음. 다만 원장이 커지면 계좌별 스냅샷을 주기적으로 만들어 정합성 배치의
스캔 범위를 줄이는 최적화가 필요해진다.

## ADR-008

### 평균단가 대신 총매입금액을 저장한다

**맥락** — 평균단가는 `(기존수량×기존단가 + 체결수량×체결가) / (기존수량+체결수량)`이다. 기존
값을 읽어야 계산되므로 read-modify-write가 불가피해 보인다. C1의 조건부 UPDATE 기법을 쓸 수 없다.

**결정** — `avg_cost`가 아니라 `total_cost`(총매입금액)를 저장한다. 평균단가는 조회 시
`total_cost / quantity`로 계산한다.

**근거** — 나눗셈을 저장하면 read-modify-write가 되지만, **덧셈으로 분해하면 원자적으로 만들 수
있다.**

```sql
UPDATE position
   SET quantity   = quantity   + :qty,
       total_cost = total_cost + :qty * :price
 WHERE account_id = :aid AND code = :code;
```

읽지 않으므로 경쟁이 없다. 락도 재시도도 필요 없다. **동시성 문제를 락으로 푸는 대신 자료구조
선택으로 없앤 것**이고, 이 프로젝트에서 가장 배울 가치가 있는 패턴 중 하나다.

**결과** — `quantity`가 0이 되면 `total_cost`도 정확히 0이어야 한다. 부동소수점을 썼다면 여기서
잔여물이 남아 평균단가가 무한이 된다(ADR-006이 정수를 쓰는 또 하나의 이유). DB 제약으로 못박았다.

```sql
CONSTRAINT position_zero_qty_zero_cost CHECK ((quantity = 0) = (total_cost = 0))
```

**배제한 대안** — 비관적 락으로 평균단가를 읽고 계산하기. 동작하지만 같은 종목에 체결이 몰릴 때
락 경합이 생기고, 애초에 필요 없는 락이다.

**재고 시점** — 선입선출(FIFO) 원가법을 도입해야 할 때. 이동평균법과 달리 매수 로트를 개별
추적해야 하므로 `position_lot` 테이블이 추가된다. 세금 계산이 정확해야 할 때만 필요하다.

## ADR-009

### 불변식을 애플리케이션과 DB에서 이중 방어

**맥락** — `available_cash >= 0` 같은 규칙을 어디서 검증할지. 애플리케이션 로직이면 충분하지
않은가.

**결정** — §03의 불변식 7개를 애플리케이션 로직과 DB 제약에서 **모두** 방어한다.

**근거** — 애플리케이션 검증은 코드에 버그가 있으면 뚫린다. 그리고 이 프로젝트가 다루는 버그는
바로 그 종류다 — 동시성 버그는 정상 경로 테스트를 전부 통과하면서 특정 타이밍에만 발생한다.
DB 제약은 어떤 코드 경로로 들어와도 적용되므로 마지막 방어선이 된다.

중요한 태도: **제약 위반 예외가 발생하면 그것은 장애가 아니라 버그 리포트다.** DB가 막아준
것은 데이터가 안전하다는 뜻이고, 그 스택트레이스가 동시성 버그의 위치를 알려준다. 그래서
제약을 "혹시 모르니 넣는 안전장치"가 아니라 **진단 도구**로 취급한다.

**결과** — Phase 0의 완료 조건이 "앱이 뜬다"가 아니라 "불변식이 DB 레벨에서 실제로 막힌다"가
됐다. `BaselineSchemaTest`가 INV-1·3·4·5·6·7을 각각 위반시켜 차단되는 것을 확인한다.

**배제한 대안** — 애플리케이션 검증만. 성능상 이점이 있다고 하지만, CHECK 제약의 비용은 무시할
수준이고 잃는 것이 너무 크다.

**재고 시점** — 없음.

## ADR-011

### 이벤트 버스는 Redis Streams로 시작, Kafka는 나중

**맥락** — §06 C3의 종목별 직렬화는 "파티션 키 = 종목코드"로 구현한다. Kafka가 정석이다.

**결정** — Phase 3까지는 Redis Streams(또는 인메모리 채널)로 시작하고, 인스턴스를 2대 이상
띄우는 시점에 Kafka로 교체한다. **이벤트 발행 인터페이스는 처음부터 추상화**한다.

**근거** — 단일 인스턴스로도 C1~C6를 전부 겪는다. 예수금 이중 차감, 취소와 체결의 경쟁, 멱등성,
백프레셔는 모두 한 프로세스 안에서 발생한다. Kafka를 먼저 넣으면 브로커 운영·컨슈머 그룹·오프셋
관리라는 별개의 학습 부담이 동시성 학습 앞에 놓인다.

**결과** — Phase 3에서 종목별 직렬화를 코루틴 `Channel`(액터)로 먼저 구현한다. Kafka로 옮길 때
파티션 키가 그 역할을 대신하므로, 개념은 그대로이고 경계만 프로세스 밖으로 나간다. 개념을 먼저
이해하고 인프라를 나중에 붙이는 순서다.

**재고 시점** — 인스턴스를 2대 이상 띄울 때. 그 시점에 리밸런싱 중 이중 처리 문제가 새로
생기므로, `execution` 테이블의 `UNIQUE (order_id, seq)` 제약이 미리 준비되어 있다.

## ADR-012

### 시세는 한국투자증권 KIS Open API

> **⛔ 대체됨 (2026-11-25)** — [ADR-021](#adr-021). 키움을 배제한 근거였던 "Windows COM
> 의존"은 OpenAPI+ 시절의 것으로, 2025년 3월 키움 REST API 출시로 소멸했다. 앱키 발급
> 시점에 키움으로 전환했다. 아래 본문은 당시 판단의 기록으로 남긴다.

**결정** — KIS Open API. 계좌를 개설한다.

**근거** — 국내 주식 실시간 체결가·호가를 무료로 WebSocket으로 제공하는 사실상 유일한

**결과** — 두 가지 장애 시나리오가 따라온다. 접근토큰이 24시간마다 만료되고 발급 호출 자체에

**API 키는 저장소에 커밋하지 않는다.** 환경변수로만 주입한다.

**재고 시점** — 미국 주식 확장 시(§13) KIS의 해외 시세를 쓸지, Polygon/Finnhub를 쓸지 재검토.

## ADR-013

### Testcontainers를 Phase 0부터, 싱글턴 컨테이너로

**결정** — Phase 0에서 Testcontainers를 세팅한다. 컨테이너는 `@Container`가 아니라 static
필드에서 한 번만 시작해 JVM 전체에서 재사용한다.

**근거**
- *Phase 0부터인 이유*: 동시성 테스트는 mock DB로 검증할 수 없다. 조건부 UPDATE의 원자성,
  UNIQUE 제약, 데드락은 실제 PostgreSQL에서만 발생한다. Phase 3에서 급하게 붙이면 그때 이미
  mock 기반 테스트가 쌓여 있어 되돌리기 어렵다.
- *싱글턴 컨테이너인 이유*: `@Container`는 테스트 클래스마다 컨테이너를 새로 띄운다. Phase 3에서
  동시성 테스트를 수백 번 반복 실행할 때(§12 — 경쟁 조건은 확률적으로 재현되므로 반복이 필수)
  이 차이가 결정적이다.

**결과** — 컨테이너 상태가 테스트 간에 공유되므로 테스트가 서로 간섭하지 않게 설계해야 한다.
`BaselineSchemaTest`는 `@Transactional` 대신 테스트마다 고유한 `user_id`를 쓴다. 제약 위반이
발생하면 Postgres가 해당 트랜잭션을 중단시켜 "위반시키고 → 다시 조회"가 한 트랜잭션 안에서
불가능하기 때문이다.

**재고 시점** — 없음.

## ADR-014

### 신용·증거금 거래는 범위에서 제외

**결정** — 현금 100%로만 거래한다. 신용융자, 증거금률, 반대매매를 구현하지 않는다.

**근거** — 증거금 거래는 도메인 복잡도를 크게 늘리지만(증거금률 산정, 담보 평가, 유지증거금
미달 시 반대매매) **동시성 측면에서 새로 배울 것이 거의 없다.** 여전히 잔고 차감과 조건부
UPDATE의 문제다. 학습 대비 비용이 나쁘다.

**결과** — `position.quantity >= 0`을 예외 없이 강제할 수 있다(INV-3). 공매도가 없으므로
음수 포지션이라는 개념 자체가 없고, 제약이 단순해진다.

**재고 시점** — 도메인 자체를 더 깊이 파고 싶어질 때. 그때는 동시성이 아니라 금융 도메인
학습이 목적이 된다.

## ADR-015

### Kotest(도메인) + JUnit 5(통합) 혼용

**결과** — 두 러너가 공존한다. Gradle의 `useJUnitPlatform()` 하나로 둘 다 실행되므로 실제

## ADR-016

### 국내 주식을 먼저 완성하고 미국 주식으로 확장

**결정** — Phase 1~6은 국내(KOSPI/KOSDAQ)만. Phase 7에서 미국 주식을 붙인다.

옳았다는 증거이고, 코드를 뜯어야 하면 틀렸다는 증거다. 이 피드백을 받는 것이 Phase 7의 진짜
목적이다.

**재고 시점** — 없음.

## ADR-017

### 초성은 애플리케이션이 계산해 컬럼에 저장한다

**맥락** — §F1.2 의 초성 검색(`ㅅㅅㅈㅈ` → 삼성전자)을 지원하려면 종목명의 초성을 어딘가에
두어야 한다. 한글 초성 추출은 유니코드 산술이다 — 음절 코드는
`0xAC00 + (초성 × 588) + (중성 × 28) + 종성` 으로 규칙적으로 배열되어 있어 나눗셈 한 번이면
끝난다. 그래서 DB 에서도 애플리케이션에서도 구현할 수 있다.

**결정** — `core-domain` 의 순수 함수 `Chosung.of()` 로 계산하고, 결과를
`instrument.name_chosung` 컬럼에 `NOT NULL` 로 저장한다.

**근거**
- *순수 함수인 이유*: 프레임워크도 DB 도 없이 완성형 음절 **11,172 개 전부**를 테스트로 돌릴
  수 있다(§12). 표본을 뽑을 이유가 없는 유한한 입력 공간이다. PL/pgSQL 이면 같은 검증에
  컨테이너가 필요하고, 규칙을 고칠 때 마이그레이션이 따라온다.
- *저장하는 이유*: 질의마다 계산하면 인덱스를 탈 수 없다.
- *`NOT NULL` 인 이유*: NULL 을 허용하면 동기화 배치가 한 번 빠뜨린 종목이 **검색에서 조용히
  사라진다.** 조용한 누락보다 시끄러운 INSERT 실패가 낫다. ADR-009 의 이중 방어와 같은 태도다.

**배제한 대안** — 생성 컬럼(`GENERATED ALWAYS AS ... STORED`). DB 가 정합성을 보장해준다는
점에서 분명히 매력적이고, ADR-009 의 "DB 가 마지막 방어선" 원칙에도 더 맞는다. 그런데
`IMMUTABLE` 한 SQL 함수로 초성 산술을 **한 벌 더** 구현해야 한다. 같은 규칙의 구현이 Kotlin 과
PL/pgSQL 에 둘로 존재하면 언젠가 어긋나고, **어긋난 것을 알아챌 방법이 없다.** 이중 방어는
서로 다른 층위에서 같은 불변식을 확인할 때 가치가 있지 같은 계산을 두 번 적을 때가 아니다.

**결과** — 정합성 책임이 애플리케이션에 있다. 저장 경로가 `Chosung.of()` 를 반드시 지나야
하며, 종목명을 바꾸면서 초성을 안 바꾸는 코드를 DB 가 막아주지 못한다. 대신 Kotlin 쪽 구현을
전수 테스트로 고정했다.

**검색어도 같은 함수를 지난다.** 저장값만 정규화하면 `lg전자` 같은 입력이 조용히 안 맞는다.
그래서 `Chosung.of()` 는 **멱등**이어야 하고(`of(of(x)) == of(x)`), 이를 속성 테스트로 고정했다.
초성을 호환 자모(U+3131~)로 통일한 것도 같은 이유다 — 음절을 분해하면 나오는 것은 한글 자모
영역(U+1100~)의 초성이지만 키보드로 입력되는 것은 호환 자모라, 눈으로 같은 `ㄱ` 이어도
코드포인트가 달라 비교가 실패한다.

**재고 시점** — 종목명 외의 텍스트에도 초성 검색이 필요해지거나, 애플리케이션을 거치지 않는
적재 경로(외부 ETL 등)가 생길 때. 그때는 생성 컬럼의 정합성 보장이 중복 구현 비용을 이긴다.

## ADR-018

### 방지턱과 권한 경계를 구분한다 — TRUNCATE 가드의 한계

**맥락** — Phase 0 검증에서 INV-4(원장 append-only)에 구멍을 발견했다. V1 의
`ledger_append_only` 는 `BEFORE UPDATE OR DELETE ... FOR EACH ROW` 라 **행 단위**로만 발화한다.
`TRUNCATE` 는 행을 하나씩 지우는 것이 아니라 테이블 파일을 통째로 버리는 DDL 에 가까운
연산이라, 행 트리거도 `DELETE` 권한 검사도 우회한다. 검증 중 실제로 원장이 통째로 지워졌다.

**결정** — V2 에서 `BEFORE TRUNCATE ... FOR EACH STATEMENT` 트리거를 추가한다. 다만 이것을
**권한 경계가 아니라 사고 방지턱으로 규정**하고, 진짜 방어선인 DB 역할 분리는 Phase 6 으로
미룬다.

**근거** — 테이블 소유자(지금 애플리케이션이 쓰는 `stockstudy` 역할)는
`ALTER TABLE ... DISABLE TRIGGER` 로 끄거나 `DROP TRIGGER` 로 지울 수 있다. 즉 이 트리거는
**악의가 아니라 실수를 막는다.** 그걸 알면서 지금 넣는 이유는, 원장을 날리는 사고의 대부분이
악의가 아니라 운영 중 손으로 친 SQL 이기 때문이다.

**배제한 대안** — 지금 당장 역할을 분리하는 것. 애플리케이션 역할에서 테이블 소유권을 떼면
Flyway 마이그레이션 실행 권한도 같이 설계해야 하고, 로컬 개발 편의가 크게 나빠진다. Phase 0~5
에서 얻는 것보다 잃는 것이 많다.

**결과** — 보안 문서에 "원장은 보호된다"고 적을 때 **어느 수준으로** 보호되는지 함께 적어야
한다. 방지턱을 경계로 착각하는 것이 이런 가드의 가장 큰 위험이다. 같은 성격의 장치가 하나 더
있다 — ADR-019 의 pre-commit 훅도 `--no-verify` 로 우회된다.

**함께 발견한 것** — `execution` 에는 append-only 트리거가 **아예** 없다. 체결을 불변으로
못박는 것은 버그 수정이 아니라 설계 결정이라(부분체결 정정·취소를 새 행으로 표현할지 수정으로
표현할지와 묶인다) 열린 질문 Q7 로 분리했다.

**재고 시점** — Phase 6 운영 준비. 그때 소유권 분리와 함께 이 트리거의 위상을 다시 적는다.

## ADR-019

### 저장소는 공개, 비밀정보는 저장소 안의 훅으로 막는다

**맥락** — 저장소를 GitHub 에 **공개(public)** 로 올렸다. Phase 1 부터 KIS 앱키·앱시크릿과
텔레그램 봇 토큰이 로컬에 존재한다. 공개 저장소에서 **한 번 푸시된 비밀은 되돌릴 수 없다** —
커밋을 지워도 GitHub 는 orphan commit 을 한동안 보관하고, 봇이 수 초 안에 긁어간다.

**결정** — `.gitignore` 위에 pre-commit 훅을 한 겹 더 둔다. 훅은 `.githooks/` 에 두어
**버전 관리하고**, `core.hooksPath` 설정은 Gradle `installGitHooks` 태스크가 대신 한다.

**근거** — `.gitignore` 가 막는 것은 "실수로 `git add`" 하나뿐이다. 남는 경로가 둘이다.

| 경로 | 막는 수단 |
| --- | --- |
| `git add -f .env` | 훅 — 파일명으로 차단 |
| `application.yml` 에 키 직접 기입 | 훅 — 스테이징된 추가 라인 검사 |

`.git/hooks` 는 커밋되지 않아 클론하면 사라진다. 저장소 안에 두면 훅 자체가 리뷰 대상이 되고
이력이 남는다. 다만 `core.hooksPath` 설정은 클론마다 한 번 필요한데, **사람이 기억하게 하지
않는다** — `checkDomainPurity`(ADR-005) 와 같은 방침으로 빌드가 강제한다.

**배제한 대안**
- *저장소를 비공개로* — 사용자가 공개를 선택했다. 공개는 학습 기록을 남긴다는 목적에 맞고,
  대신 방어를 한 겹 더 두는 쪽으로 대응했다.
- *gitleaks·detect-secrets 등 기성 도구* — 더 똑똑하지만 설치 의존성이 생긴다. 막아야 할
  패턴이 KIS·텔레그램 등 소수로 특정되어 있어 POSIX sh 20 줄로 충분하다. 패턴이 늘어나면 재고.

**결과와 한계** — 이것도 ADR-018 과 같은 **방지턱**이다.
- `git commit --no-verify` 로 우회된다
- 이미 푸시된 것은 막지 못한다 (공개 시점에 이력 전체를 스캔해 깨끗함을 확인했다)
- **KIS 앱키 자체는 형태로 구분되지 않는다.** `PS` 로 시작하는 36 자 영숫자라 일반 문자열과
  다르지 않다. 그래서 변수명·YAML 키 기준으로만 잡는다. 이름 없는 문자열 리터럴에 박아넣으면
  통과한다

오탐은 줄 끝에 `pragma: allowlist secret` 으로 해제한다.

**재고 시점** — 비밀의 종류가 늘어나거나 협업자가 생길 때. 그때는 기성 도구 + CI 쪽 스캔을
함께 건다. 훅은 로컬에서만 돌아서 우회 가능하므로, 협업 시점에는 서버 쪽 검사가 필요하다.

## ADR-020

### KIS 는 모의투자를 기본값으로, 실전은 설정으로만 전환

> **♻️ 원칙은 유지, 대상만 교체 (2026-11-25)** — "모의투자 기본값, 실전 전환은 환경변수
> 교체만으로"라는 원칙은 [ADR-021](#adr-021)의 키움 전환 후에도 그대로다. 키움도 실전과
> 모의의 앱키·앱시크릿·도메인이 전부 별개라 이 결정의 전제가 동일하게 성립한다. 아래
> 본문의 KIS 고유 수치(도메인, `EGW00201`)는 키움 값으로 대체된다 — ADR-021 참조.

**맥락** — ADR-012 에서 KIS Open API 를 쓰기로 했다. 실제로 신청해 보니 **실전투자와
모의투자는 앱키·앱시크릿·도메인이 전부 별개**였다. 실전 키로 모의투자 API 를 호출하면 인증
오류가 난다. 둘을 섞어 쓸 수 없다.

**결정** — `.env.example` 의 `KIS_BASE_URL` 기본값을 모의투자
(`openapivts.koreainvestment.com:29443`) 로 둔다. 실전 전환은 환경변수 교체만으로 이뤄지게 하고,
코드에는 어느 쪽도 하드코딩하지 않는다.

**근거** — 이 프로젝트는 Phase 3 에서 **실제로 주문을 넣는다.** 동시성 버그 하나가 실전
계좌에서는 진짜 돈이다. 모의투자에서도 국내주식 현재가·체결·일봉과 웹소켓 실시간 시세가 모두
제공되므로 Phase 1~3 을 전부 모의로 완주할 수 있다. 위험을 감수해서 얻는 것이 없다.

**결과 — Phase 1 에서 만나게 될 것**
- 모의투자 계좌는 **REST 호출 유량 제한이 더 낮다**(공식 문서 명시). 종목마스터 동기화
  배치에서 `EGW00201`(초당 거래건수 초과)를 만나게 된다. 이건 버그가 아니라 설계 과제다 —
  레이트 리미터가 필요하다는 신호이고, §R 에 항목을 추가해야 한다.
- 접근토큰은 24 시간 만료 + 발급 호출 자체에 제한이 있다(ADR-012). §R3 토큰 갱신 레이스를
  Phase 1 의 KIS 클라이언트에서 바로 만난다.

**미확인 — Phase 2 에서 직접 측정할 것** — 커뮤니티에서는 웹소켓이 **앱키당 동시 세션 1 개,
세션당 실시간 등록 41 종목**으로 제한된다고 보고하지만, 공식 문서에서 수치를 확인하지 못했다.
사실이라면 설계에 직접 영향을 준다 — 인스턴스를 여러 대 띄울 수 없고(ADR-011 의 Kafka 전환
전제와 충돌한다), 41 종목을 넘으면 구독 슬롯 관리가 필요하다. **추정을 설계 전제로 삼지 않고,
Phase 2 에서 실제로 붙여 보고 확인되는 값을 여기에 적는다.**

**재고 시점** — 실제 자금으로 거래하고 싶어질 때(ADR-001 재고와 묶인다). 그때 필요한 것은
코드 변경이 아니라 키 교체여야 한다. 그렇지 않다면 이 결정이 제대로 구현되지 않은 것이다.

## ADR-021

### 증권 API 를 KIS 에서 키움 REST API 로 전환

**맥락** — Phase 1 이 KIS 앱키 발급(사람이 직접)에서 막혀 있던 중 대안을 재검토했다.
ADR-012 가 키움을 배제한 근거는 "OpenAPI+ 가 Windows COM 의존이라 macOS 불가"였는데,
키움이 2025년 3월 **크로스플랫폼 REST + WebSocket API 를 정식 출시**하면서 그 근거가
소멸했다. 아직 코드가 한 줄도 KIS 에 붙지 않은 지금이 전환 비용이 0 인 유일한 시점이다.

**결정** — 시세·주문 API 를 **키움 REST API** 로 전환한다. ADR-020 의 원칙(모의투자
기본값, 실전 전환은 환경변수 교체만)은 그대로 승계한다.

| | 모의투자 (기본값) | 실전투자 |
| --- | --- | --- |
| REST | `https://mockapi.kiwoom.com` | `https://api.kiwoom.com` |
| WebSocket | `wss://mockapi.kiwoom.com:10000` | `wss://api.kiwoom.com:10000` |

웹소켓의 정확한 경로는 커뮤니티 자료 간에 표기가 갈려서(`/api/dostk/websocket` 등)
Phase 2 구현 시 공식 가이드로 확인하고 여기에 적는다.

**근거**
- *웹소켓 한도가 공식 문서에 있다* — 세션당 실시간 시세 **200 종목**(공식). KIS 는
  커뮤니티 추정 41 종목을 공식 문서에서 확인하지 못해 "실측 전까지 미지수"(구 Q8)였다.
  Phase 2 의 설계 리스크가 추정에서 문서로 바뀐다.
- *발급 절차 비용은 양쪽이 동일하다* — 계좌 개설·본인 인증·모의투자 신청·앱키 발급 모두
  사람이 직접 해야 하는 점은 같다. 전환으로 잃는 것이 없다.
- *국내 개인 투자자 커뮤니티 자료가 가장 풍부하다* — 레퍼런스 부족으로 막힐 확률이 낮다.

**배제한 대안**
- *KIS 유지* — 공식 문서·예제 품질은 가장 좋으나, 웹소켓 한도 미확인 리스크(구 Q8)와
  모의투자 유량 제한 이슈(`EGW00201`)가 그대로 남는다.
- *LS증권* — REST + WebSocket 은 제공하나 커뮤니티 자료가 상대적으로 적다.
- *토스증권* — 2026-08 오픈 API 정식 출시 (REST + WebSocket, 주문·조건주문, 호출 한도
  공식 명시). 그러나 **모의투자 환경이 없다** — 서버가 실전(`openapi.tossinvest.com`)
  하나뿐이라 체결·원장 동시성 테스트를 실계좌 돈으로 해야 한다. ADR-020 전제와 양립
  불가. 실전 전환 시점(ADR-001 재고)에는 재검토 가치 있음.

**결과 — KIS 전제로 적어 둔 것들이 이렇게 바뀐다**
- 환경변수 `KIS_*` → `KIWOOM_*`. pre-commit 훅의 비밀정보 패턴도 함께 갱신 (ADR-019)
- 접근토큰은 `POST /oauth2/token` (client_credentials). 만료 정책·발급 호출 제한은 KIS 와
  다를 수 있으므로 **§R3(토큰 갱신 레이스)의 전제 수치는 Phase 1 구현 시 공식 문서로
  재확인**한다. 레이스 자체는 토큰 캐시 구조상 동일하게 존재한다
- 모의투자 REST 호출 제한은 **계좌(토큰)별 TR 1 개당 초당 1 회** 수준으로 더 빡빡하다.
  레이트 리미터가 필요하다는 설계 과제(§R)는 그대로 유지되며, KIS 의 `EGW00201` 레퍼런스는
  키움 에러코드로 대체한다
- 앱키 발급 시 **IP 등록이 필수**이고(등록된 IP 에서만 인증 가능), App Key·Secret
  다운로드는 **1 회만** 가능하다. IP 가 바뀌는 환경(노트북 이동 등)에서는 포털에서 IP 를
  갱신해야 한다 — 운영 문서에 적어 둘 것
- 실전·모의 앱키 분리는 KIS 와 동일 — ADR-020 의 이중 차단(ADR-019 훅) 전제 유지

**재고 시점** — ① Phase 2 웹소켓 실측에서 공식 한도와 다른 동작을 발견할 때.
② 미국 주식 확장 시(§13) 키움 REST 의 해외 시세·주문 지원 범위를 Polygon/Finnhub 와 재비교.

## ADR-022

### 비밀값은 타입으로 가두고, 유출 부재를 테스트로 증명한다

**맥락** — 키움 앱키·앱시크릿·토큰이 코드에 들어오기 시작한다. 이 값들은 본인 명의 계좌의
자격증명이고, 저장소는 공개다. 기존 방어(ADR-019 의 pre-commit 훅)는 **커밋 경로**만 막는다.
실제 유출 사고의 대부분은 커밋이 아니라 **로그**에서 난다 — 요청/응답 원문 로깅, 설정 객체
`toString()`, 예외 메시지, JSON 직렬화. Kotlin 에서는 특히 위험한데, `data class` 가
`toString()` 을 자동 생성하고 문자열 보간(`"$config"`)이 그것을 아무 경고 없이 호출한다.

**결정** — 세 겹으로 방어하고, 방어가 실제로 동작하는지를 상시 테스트로 증명한다.

1. **구조적 방어 — `Secret` 타입** (`core-support`). 값을 `private` 으로 가두고
   `toString()` 은 `****` 를 돌려준다. public 프로퍼티가 없어 Jackson 직렬화는 기껏해야
   빈 객체(`{}`)를 내보낸다 — 어떤 경로로도 평문은 나가지 않는다. 평문이 필요한 지점은
   `reveal()` 을 **일부러** 호출해야 하며, 따라서 `grep "reveal()"` 한 번으로 평문이
   나가는 전 지점이 열거된다.

   *구현에서 배운 것 (하네스 V1 이 첫 실행에서 잡아낸 것들)* — ① `isBlank()` 처럼 `is`
   접두 불리언을 두면 Jackson 이 getter 로 인식해 프로퍼티가 생긴다. `blank()` 로 바꿨다.
   ② Jackson 2.19 부터 빈 빈(bean)은 예외가 아니라 `{}` 가 기본이다 — "직렬화가 즉시
   실패한다"는 fail-fast 는 버전 기본값에 기댄 가짜 보장이라 "평문 부재"로 바로잡았다.
   ③ 마스킹 패턴 적용 순서가 계약이다 — key-value 패턴을 Bearer 보다 먼저 돌리면
   `authorization=Bearer xxx` 에서 "Bearer" 만 지우고 진짜 토큰을 남긴다.
2. **그물 방어 — 로그백 마스킹 컨버터** (`api-gateway`). `appkey`·`secretkey`·`token`·
   `Bearer …`·계좌번호 패턴을 로그 메시지에서 마스킹한다. 타입을 우회한 실수(외부 응답
   원문을 통째로 로깅하는 등)를 잡는 마지막 그물이다.
3. **저장소 방어 — `guardSecrets` Gradle 태스크**. 추적되는 전체 파일을 훅과 같은 패턴으로
   스캔해 `check` 에서 실패시킨다. `git commit --no-verify` 우회와 훅 설치 이전에 들어간
   파일을 잡는다.

**검증(하네스 V1)** — 카나리아 비밀값으로 유출 경로를 **일부러 공격**하는 테스트를 `check`
에 포함한다: `toString`·문자열 보간·컬렉션 출력에 평문 부재, Jackson 직렬화 fail-fast,
마스킹 컨버터가 실제 로그 출력에서 카나리아를 지우는지. 방어 장치는 믿는 것이 아니라
증명하는 것이다.

**배제한 대안**
- *패턴 마스킹만* — 마스킹은 정규식이 아는 모양만 지운다. 새 비밀 종류가 생기면 조용히
  샌다. 구조적 방어가 1차여야 한다.
- *규율만(“로그에 찍지 말자”)* — Phase 0 에서 이미 확인한 원칙: 규율은 기계가 강제하지
  않으면 지켜지지 않는다 (ADR-009 와 같은 사상).
- *Vault 등 비밀 관리 인프라* — 단일 인스턴스 로컬 개발에 과하다. Phase 6 운영 준비에서
  재검토.

**결과** — 설정 클래스는 비밀 필드를 `String` 이 아닌 `Secret` 으로 선언해야 한다. HTTP
클라이언트는 전송 직전에만 `reveal()` 한다. JSON 구조화 로깅(logstash encoder)으로 전환할
때는 컨버터가 아니라 encoder 의 마스킹 기능으로 같은 규칙을 옮겨야 한다 — 하네스 V1 이
그 전환에서 깨지면서 알려줄 것이다.

**재고 시점** — 협업자가 생기거나 배포 환경이 분리될 때 (Vault/SSM 류 도입과 함께).

## ADR-023

### 하네스 — 지키는 것과 증명하는 것을 분리한다

**맥락** — 가드레일이 세 군데(훅, Gradle 태스크, DB 제약)에 흩어져 있고 전체 그림이
어디에도 없다. Phase 1 부터 외부 API 가 들어오면서 "무엇이 상시 강제되고 무엇이 테스트
시점에 증명되는가"의 구분이 없으면, 외부 서버 장애로 빌드가 깨지는 날 사람들이 실패를
무시하기 시작한다.

**결정** — [`harness.md`](./harness.md) 를 단일 장부로 만들고 두 축을 구분한다.

- **지키는 것(G)** — 사람의 규율을 기계로 옮긴 것. 어기면 빌드·커밋이 죽는다. 전부
  `check` 에 묶인다.
- **증명하는 것(V)** — 가설이 참인지 실험으로 보이는 것. 스위트별로 분리하되,
  **오프라인에서 도는 것은 전부 `check`**, 외부 세계가 필요한 것(라이브 스모크)은
  **opt-in 태스크**로 뺀다.

**근거** — `check` 가 항상 통과 가능해야 "깨지면 반드시 내 탓"이라는 신뢰가 유지된다. 그
신뢰가 깨지는 순간 하네스는 장식이 된다. 라이브 테스트의 실패는 버그가 아니라 **계약 변경
신호**이므로 의미 자체가 다르다 — 다른 의미의 실패를 같은 태스크에 섞지 않는다.

**결과** — 새 규칙·새 검증은 harness.md 에 먼저 적고 코드를 만든다(next-steps 의 "문서
먼저"와 동일). 외부 계약은 라이브에서 녹화한 픽스처로 오프라인 계약 테스트(V4)에 공급해
두 세계를 잇는다.

**재고 시점** — CI 가 생길 때. guard 태스크·라이브 스모크의 실행 주기를 CI 파이프라인
단계로 재배치한다.

## ADR-024

### Redis 분산락을 직접 구현한다 — 그리고 이 락은 정합성 경계가 아니다

**맥락** — §R3(접근토큰 갱신 레이스)을 막으려면 "여러 인스턴스 중 하나만 토큰을 발급한다"가
필요하다. 토큰 캐시를 Redis 에 두는 이상 락도 같은 Redis 에 두는 것이 자연스럽다. 선택지는
Redisson 같은 라이브러리를 쓰는 것과 `SET NX PX` 로 직접 만드는 것 두 가지다.

**결정** — **직접 구현한다.** `SET key owner NX PX ttl` 로 획득하고, 해제는 Lua 스크립트로
**소유자가 일치할 때만** 지운다.

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end
```

**근거**

- *락 만료·해제 레이스가 이 프로젝트가 배우려는 내용 그 자체다.* Redisson 을 붙이면
  `lock()`/`unlock()` 두 줄로 끝나고, 그 안에서 무슨 일이 일어나는지는 영영 모른다.
- *소유자 검증 없는 해제는 틀렸다.* `DEL key` 로 해제하면, A 의 임계구역이 TTL 보다
  길어져 락이 만료되고 B 가 새로 잡은 뒤에 A 가 뒤늦게 `DEL` 하는 순간 **B 의 락을 A 가
  푼다.** GET-비교-DEL 을 원자적으로 묶어야 하고, Redis 에서 원자성의 단위는 Lua 다.
- *해제 실패는 신호다.* 스크립트가 0 을 돌려주면 "내가 들고 있던 락이 이미 내 것이 아니다"
  — 즉 **임계구역이 TTL 을 넘겼다**는 뜻이다. 조용히 넘기지 않고 경고 로그로 남긴다.
  TTL 을 늘려야 한다는 유일한 객관적 증거다.

**이 락으로 지킬 수 없는 것 — 명시적으로 못박는다**

Redis 단일 인스턴스 락은 **정합성 경계가 아니다.** 다음 경우에 둘 이상이 동시에 임계구역에
들어간다.

1. 임계구역이 TTL 보다 길어진 경우 (GC 정지, 네트워크 지연)
2. 마스터가 락을 복제하기 전에 죽고 레플리카가 승격된 경우

따라서 **이 락은 "상호 배제 보장"이 아니라 "중복 작업 억제(thundering herd 방지)"로만
쓴다.** 토큰 발급이 두 번 일어나도 결과는 발급 호출 한 번이 낭비되는 것뿐이므로 이 용도에는
정확히 맞는다.

**Phase 3 의 돈은 이 락으로 지키지 않는다.** 예수금 차감·체결 반영의 정합성 경계는 DB 다 —
조건부 `UPDATE ... WHERE available_cash >= ?` 의 원자성과 INV-1 CHECK 제약이 진짜 방어선이고
(ADR-009), 분산락은 그 위에 얹는 성능 최적화일 뿐이다. 락을 정합성의 근거로 삼는 순간
Kleppmann 이 지적한 함정("fencing token 없는 락은 안전하지 않다")에 그대로 들어간다.

**배제한 대안**

- *Redisson* — watchdog 자동 연장, RedLock, 재진입까지 들어 있어 운영에는 더 안전하다.
  그러나 배우려는 것을 전부 감춘다. 운영 전환(Phase 6) 시 재검토한다.
- *RedLock (N 개 노드 과반)* — 단일 Redis 로 운영하는 현 구성에서는 적용 대상 자체가 없고,
  위 2번(복제 레이스)을 풀어도 1번(GC 정지)은 그대로 남는다. 비용 대비 얻는 것이 적다.
- *DB 행 잠금(`SELECT ... FOR UPDATE`)* — 정합성은 더 강하지만, 토큰 캐시가 Redis 에
  있는데 락만 DB 에 두면 두 저장소의 상태가 갈라질 수 있다. **락과 그 락이 지키는 상태는
  같은 곳에 둔다.**

**결과** — 임계구역은 TTL 보다 확실히 짧아야 한다. 토큰 발급 HTTP 타임아웃을 락 TTL 보다
작게 잡아, 타임아웃이 먼저 터지도록 강제한다. 락을 못 잡은 쪽은 **기다렸다 캐시를 읽는다** —
대기 데드라인까지 획득 재시도와 캐시 확인을 번갈아 하고, 끝내 못 얻으면 예외로 실패한다.
조용히 직접 발급하면 락을 둔 의미가 사라진다.

구현 위치는 당분간 `market-data` 다. Phase 3 에서 `trading` 도 필요해지면 그때
`core-infra` 모듈로 승격한다 — 지금 모듈을 만들면 사용처가 하나뿐인 모듈이 생긴다.

**재고 시점** — ① 인스턴스를 2대 이상 띄워 실제로 레이스를 관측할 때. ② Redis 를 HA 구성
(Sentinel/Cluster)으로 바꿀 때 — 위 2번 실패 모드가 현실이 된다.

## ADR-025

### 레이트 리밋은 간격 예약으로, 시각은 Redis 서버에서 읽는다

**맥락** — 키움 모의투자의 REST 한도는 **계좌(토큰)별 TR 1 개당 초당 1 회** 수준이다.
Phase 1 §3.3 의 종목마스터 동기화는 같은 TR(ka10001)을 수천 번 호출하는 배치라, 아무
대책 없이 돌리면 몇 초 만에 막힌다. 이건 버그가 아니라 설계 과제다 (ADR-021 에서 예고).

**결정** — Redis 에 **다음 호출 허용 시각을 예약**하는 방식으로 간격을 강제한다. Lua
스크립트 한 번에 "읽고-계산하고-예약"이 원자적으로 일어나고, 호출부에는 **기다려야 할
시간**을 돌려준다.

```
A (t=0)  → 예약 없음. 즉시 통과, next = 1000 예약
B (t=10) → 990ms 기다리라고 답하고, next = 2000 예약
C (t=20) → 1980ms 기다리라고 답하고, next = 3000 예약
```

**근거**

- *토큰 버킷이 아닌 이유* — 버킷의 장점은 버스트 허용인데, 여기서는 버스트가 정확히
  막으려는 것이다. 한도가 "초당 N 개"가 아니라 사실상 "연속 호출 사이의 간격"이다.
- *거부가 아니라 대기시간을 돌려주는 이유* — 거부하면 재시도 책임이 호출부로 넘어가고,
  재시도 간격을 각자 정하는 순간 thundering herd 가 돌아온다. 정확히 얼마나 자면 되는지
  알려주면 호출부는 그만큼만 잔다. 가상 스레드에서 이 대기는 캐리어를 잡지 않는다 (ADR-003).
- *시각을 `redis.call('TIME')` 으로 읽는 이유* — 인스턴스마다 벽시계가 조금씩 다르다.
  클라이언트 시각으로 예약하면 시계가 앞선 인스턴스가 남의 자리를 밀고 들어간다. 비교
  기준이 하나여야 한다.
- *한도를 넘으면 예약하지 않는 이유* — 거부해놓고 자리를 잡으면 아무도 쓰지 않는 슬롯이
  흘러간다. 거부는 거부로 끝나야 한다.
- *기본 간격이 1 초가 아니라 1.1 초인 이유* — 경계는 서버 시계로 판정된다. 정확히 1 초로
  쏘면 네트워크 지연이 조금만 흔들려도 경계 안쪽에 걸린다. 여유 10% 는 막혔을 때 치르는
  비용보다 싸다.

**이 리미터가 지킬 수 없는 것** — **협조적** 제한이다. 이 경로를 지나지 않는 호출은 막지
못한다. 그래서 키움 호출은 전부 클라이언트를 통하게 두고, 클라이언트가 리미터를 지나게
배선한다. 또한 Redis 가 죽으면 제한도 함께 죽는다 — 그때는 호출 자체가 실패하는 편이
안전하므로 예외를 삼키지 않는다.

**배제한 대안**

- *Resilience4j RateLimiter* — 인스턴스 안에서만 동작한다. 인스턴스를 늘리는 순간 한도가
  N 배로 뚫린다. 한도는 **계좌 단위**이지 프로세스 단위가 아니다.
- *Bucket4j + Redis* — 분산 토큰 버킷으로 성숙한 선택지지만, 위에서 말한 대로 버스트
  허용이 여기서는 단점이다. 그리고 ADR-024 와 같은 이유로, 이 수준의 메커니즘은 직접
  만들어 보는 편이 배우는 것이 많다.
- *무조건 `Thread.sleep(1초)`* — 단일 인스턴스에서만 맞고, 여러 호출 경로가 생기는 순간
  합산 호출량을 아무도 모르게 된다.

**결과** — 배치 설계가 달라진다. 종목 수천 건을 TR 하나로 긁으면 초당 1 건이라 수 시간이
걸린다. §3.3 의 종목마스터 동기화는 **종목별 조회가 아니라 목록 조회 TR** 을 찾아 쓰거나,
야간 배치로 돌리는 것을 전제로 설계해야 한다. 한도가 설계를 바꾼다.

**재고 시점** — ① 실전 전환 시 한도가 달라질 때(모의가 더 빡빡하다). ② 호출 경로가
늘어 TR 단위가 아니라 계좌 전체 합산 한도가 문제가 될 때.
