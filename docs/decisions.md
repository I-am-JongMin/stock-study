## ADR-001

### 체결은 자체 엔진이 판정한다

**맥락** — "구매까지 할 수 있다"를 구현하는 방법이 두 가지다. 증권사 주문 API로 전달하거나,
우리가 직접 체결을 판정하거나.

**결정** — 자체 체결 엔진(모의 거래). 시세만 외부에서 실시간으로 받는다.

**근거** — 학습 목표 네 개 중 가장 어려운 것이 동시성인데, **동시성 문제는 잔고와 주문 상태를
우리가 소유할 때만 발생한다.** 증권사 프록시 방식을 택하면 잔고 검증·주문 상태 전이·체결
반영이 모두 증권사 서버 안에서 일어나고, 우리 쪽에는 HTTP 호출과 응답 매핑만 남는다. C1(예수금
이중 차감)이나 C2(취소와 체결의 경쟁)를 겪을 기회 자체가 사라진다.

**배제한 대안** — 증권사 주문 API 프록시. 외부 장애 대응 학습에는 더 좋지만, 그 목표는 시세
파이프라인(§07 R1~R3)만으로도 충분히 달성된다. 계좌 개설이 필요하다는 부담도 있다.

**결과** — 오더북·체결 규칙·원장을 직접 구현해야 하므로 Phase 3의 분량이 크게 늘어난다. 이건
비용이 아니라 목표다.

**재고 시점** — 실제 자금으로 거래하고 싶어질 때. 그때는 체결 엔진을 버리는 것이 아니라
`ExecutionGateway` 인터페이스의 구현을 하나 더 붙이는 형태가 된다.

## ADR-002

### 체결 상대방은 가상 유동성 공급자

**맥락** — 자체 체결 엔진을 만들면 "누구와 체결하는가"를 정해야 한다.

**결정** — 외부 실시간 시세를 기준으로 즉시 체결을 판정하는 가상 상대방을 둔다. 사용자 간
매칭도 가능하도록 오더북은 그대로 유지한다.

**근거** — 사용자 간 매칭만 구현하면 **혼자 테스트할 때 주문이 영원히 체결되지 않는다.** 체결이
일어나지 않으면 원장·포지션·평균단가·체결 알림을 검증할 방법이 없고, Phase 3~4가 통째로
막힌다. 가상 상대방을 두면 가격-시간 우선 오더북 로직은 그대로 배우면서 체결이 실제로 발생한다.

**배제한 대안** — 사용자 간 매칭 전용. 이론적으로 더 "진짜"지만 검증 불가능한 시스템은 학습
가치가 없다.

**결과** — `execution.counter_order_id`가 nullable이다. NULL이면 가상 상대방과의 체결이다.
체결 가격은 시세가 `stale`일 때 신뢰할 수 없으므로, 그 상태에서는 시장가 주문을 거부한다(§R1).

**재고 시점** — 실제 사용자가 여러 명 붙어 오더북에 물량이 쌓이기 시작할 때. 가상 공급자를
"오더북에 유동성이 없을 때만" 동작하게 축소할 수 있다.

## ADR-003

### Spring MVC + 가상 스레드 (WebFlux 아님)

**맥락** — 초당 수천 건의 시세를 받아 다수 클라이언트에 밀어야 한다. 전통적으로는 WebFlux를
떠올리는 요구사항이다.

**결정** — Spring MVC를 쓰고 `spring.threads.virtual.enabled=true`로 가상 스레드를 켠다.

**근거** — 학습 목표는 **락과 트랜잭션의 이해**다. WebFlux는 `Mono`/`Flux` 체인 때문에 "어디서
락이 잡히고 어디서 트랜잭션 경계가 끝나는지"를 읽기 어렵게 만든다. `@Transactional`이 리액티브
체인에서 어떻게 동작하는지 자체가 별도의 난제이고, 그 난제는 이 프로젝트가 배우려는 것이
아니다. Java 21의 가상 스레드는 블로킹 코드를 그대로 유지하면서 스레드당 메모리 비용을 없애므로,
코드 가독성을 잃지 않고 확장성만 얻는다.

**배제한 대안**
- **WebFlux** — 위 이유. 그리고 JDBC는 블로킹이므로 R2DBC로 갈아타야 하는데, R2DBC는
  `RETURNING` 절과 배치 처리에서 JDBC보다 제약이 많다.
- **플랫폼 스레드만** — SSE 커넥션 하나당 스레드 하나면 동시 구독자 수가 수천 명에서 막힌다.

**결과** — 가상 스레드는 `synchronized` 블록 안에서 블로킹하면 캐리어 스레드를 고정(pinning)한다.
그래서 락이 필요한 곳에서는 `synchronized` 대신 `ReentrantLock`을 쓴다. 이건 Phase 3에서 실제로
주의해야 할 지점이다.

**재고 시점** — 시세 팬아웃이 가상 스레드로도 한계에 부딪힐 때. 그때는 SSE 푸시 경로만
리액티브로 분리하고 주문 경로는 MVC로 남기는 하이브리드가 가능하다.

## ADR-004

### JPA를 쓰지 않고 `JdbcClient`로 SQL을 직접 쓴다

**맥락** — Kotlin + Spring Boot의 기본 선택은 Spring Data JPA다.

**결정** — JPA와 Hibernate를 쓰지 않는다. `JdbcClient`로 SQL을 직접 작성한다.

**근거** — 이 프로젝트에서 가장 중요한 기법이 **조건부 원자적 UPDATE + `affected rows` 확인**이다.

```sql
UPDATE account
   SET available_cash = available_cash - :amount
 WHERE id = :id AND available_cash >= :amount;
-- affected rows == 0 → 잔고 부족
```

문제는 JPA의 가장 자연스러운 사용법이 정확히 C1이 터지는 코드라는 점이다.

```kotlin
val account = repository.findById(id)     // SELECT
account.availableCash -= amount           // 애플리케이션에서 계산 ← 여기가 틈
repository.save(account)                  // UPDATE
```

JPA로도 `@Query`에 네이티브 SQL을 넣어 조건부 UPDATE를 할 수 있지만, 그러면 영속성 컨텍스트와
DB 상태가 어긋나 `clearAutomatically`, `flushAutomatically` 같은 옵션을 계속 신경 써야 한다.
프레임워크와 싸우는 시간이 배우는 시간을 잡아먹는다.

**배제한 대안**
- **Spring Data JPA** — 위 이유.
- **jOOQ** — 타입 안전한 SQL로 훌륭한 선택이지만 코드 생성 단계가 Phase 0을 무겁게 한다.
  쿼리가 복잡해지면 재고할 가치가 있다.
- **Exposed** — Kotlin 친화적이지만 Spring 트랜잭션 통합이 JDBC만큼 매끄럽지 않다.

**결과** — SQL 문자열을 직접 관리해야 하므로 타이포가 런타임에 발견된다. Testcontainers 통합
테스트가 이를 잡는 안전망이다(ADR-013). 읽기 전용 조회가 늘어나면 JPA를 읽기 모델에만
추가하는 선택지가 남아 있다.

**재고 시점** — 조회 쿼리가 30개를 넘어 문자열 관리 비용이 커질 때 → jOOQ.

## ADR-005

### 모듈러 모놀리스 + 도메인 순수성을 빌드로 강제

**맥락** — 6개 모듈로 나눌지, 단일 모듈로 시작할지, 처음부터 마이크로서비스로 갈지.

**결정** — Gradle 멀티모듈 모놀리스. `core-domain`은 프레임워크에 의존하지 않으며, 이를
`checkDomainPurity` Gradle 태스크가 강제한다.

**근거** — 두 부분으로 나뉜다.

*마이크로서비스를 안 하는 이유*: 주문 접수 → 예수금 예약 → 체결 → 원장 기록이 **하나의
트랜잭션**이어야 한다(INV-4). 서비스로 쪼개면 이것이 분산 트랜잭션 문제가 되고, Saga·보상
트랜잭션이라는 별개의 난제가 동시성 학습을 가려버린다. 그리고 아직 경계가 어디인지 모른다.

*모듈로 나누는 이유*: 단일 모듈이면 `core-domain`에 Spring을 쓰는 것을 막을 방법이 없다. 그런데
§12의 속성 기반 테스트(무작위 주문 수만 건으로 불변식 검증)는 도메인 로직이 Spring 컨텍스트
없이 밀리초 단위로 실행될 때만 현실적이다. 모듈 경계가 그 실행 속도를 지키는 장치다.

*빌드로 강제하는 이유*: 규칙을 문서에만 적으면 언젠가 누가 편의를 위해 Spring 의존성을 하나
추가한다. 그 시점을 사람이 코드 리뷰로 잡아내길 기대하지 않는다.

```
core-domain 순수성 위반 (§04) — 프레임워크 의존성이 발견되었습니다:
  - org.springframework:spring-context:6.2.8
  - io.micrometer:micrometer-observation:1.14.8   ← 추이적 의존성까지 잡는다
```

**배제한 대안** — 단일 모듈 + 패키지 규칙(ArchUnit). ArchUnit도 좋은 도구지만 클래스 참조를
검사할 뿐, classpath에 무엇이 있는지는 막지 못한다. 무거운 라이브러리가 테스트 실행 시간에
영향을 주는 것이 문제이므로 classpath 수준에서 막아야 한다.

**재고 시점** — 배포 단위를 실제로 분리해야 할 때(시세 수집기만 따로 스케일링). 그때는 모듈
경계가 이미 그려져 있으므로 분리 비용이 낮다. 이것이 모듈러 모놀리스의 목적이다.

## ADR-006

### 금액은 최소 단위 정수로만 보관한다

**맥락** — 금액을 `Double`, `BigDecimal`, `Long` 중 무엇으로 표현할지.

**결정** — `Money` 값 객체를 만들고 내부는 최소 단위 정수(`Long`)로만 보관한다. KRW는 원, USD는
센트. `BigDecimal`은 입출력 변환에만 쓴다.

**근거**
- `Double`은 `0.1 + 0.2 != 0.3`이다. 논쟁의 여지가 없다.
- `BigDecimal`을 내부 표현으로 쓰면 scale이 다른 값이 섞이면서 `equals`와 `compareTo`가
  갈라진다 — `BigDecimal("1.0") != BigDecimal("1.00")`인데 `compareTo`는 0을 반환한다. 잔고
  비교에서 이 불일치는 찾기 어려운 버그를 만든다.
- 정수 하나면 등가성·비교·해시가 전부 일관되고, DB의 `BIGINT` 컬럼과 1:1로 대응된다. ADR-008의
  원자적 덧셈도 정수여야 가능하다.

**결과** — 두 가지를 조용히 넘기지 않고 예외로 실패시킨다.
- 오버플로: `Math.addExact` 사용. 잔고가 음수로 감싸면 INV-1이 애플리케이션 레벨에서 무의미해진다.
- 소수점 손실: `RoundingMode.UNNECESSARY`. 0.5원을 0원이나 1원으로 만들면 원장 합계(INV-2)가
  어긋나고 원인 추적이 거의 불가능하다.

**재고 시점** — 없음. 이건 되돌릴 결정이 아니다. 다만 통화 추가(§13) 시 `Currency` enum에
항목이 늘어나며, 그때 `Money`의 산술 코드가 한 줄도 바뀌지 않아야 한다. 바뀐다면 추상화가
틀렸다는 신호다.

## ADR-007

### 원장은 append-only, 잔고 컬럼은 캐시

**맥락** — 예수금을 `account.available_cash` 컬럼만으로 관리할지, 원장(ledger)을 따로 둘지.

**결정** — 모든 금액 변동을 `ledger`에 한 줄씩 append하고, `account`의 잔고 컬럼은 빠른 조회를
위한 캐시로 취급한다. 원장의 UPDATE·DELETE는 **트리거로 차단**한다.

**근거** — 잔고 컬럼만 있으면 "지금 얼마인가"는 알 수 있지만 **"어떻게 이 값이 되었나"를 알 수
없다.** 동시성 버그로 80만원이 공짜로 생겼을 때, 잔고만 보면 언제 어디서 생겼는지 추적할
방법이 전혀 없다. 실제 금융 시스템이 복식부기를 쓰는 이유가 이것이다.

트리거로 막는 이유는 ADR-005와 같다. "원장은 수정하지 않는다"를 문서에만 적으면 언젠가 데이터를
고치려는 UPDATE가 실행된다.

```sql
CREATE TRIGGER ledger_append_only
    BEFORE UPDATE OR DELETE ON ledger
    FOR EACH ROW EXECUTE FUNCTION ledger_reject_mutation();
```

**결과** — 잔고 컬럼과 원장 합계가 어긋날 수 있다(INV-2). 그래서 `v_account_ledger_consistency`
뷰를 만들어 `drift`를 SQL 한 번으로 확인하고, Phase 6에서 이를 최고 우선순위 알람으로 건다.

**배제한 대안** — 이벤트 소싱(잔고 컬럼 없이 원장만). 조회할 때마다 전체 원장을 접어야 하므로
주문 검증 지연이 원장 크기에 비례해 늘어난다. 잔고 스냅샷 + 원장이 실용적 타협점이다.

**재고 시점** — 없음. 다만 원장이 커지면 계좌별 스냅샷을 주기적으로 만들어 정합성 배치의
스캔 범위를 줄이는 최적화가 필요해진다.

## ADR-008

### 평균단가 대신 총매입금액을 저장한다

**맥락** — 평균단가는 `(기존수량×기존단가 + 체결수량×체결가) / (기존수량+체결수량)`이다. 기존
값을 읽어야 계산되므로 read-modify-write가 불가피해 보인다. C1의 조건부 UPDATE 기법을 쓸 수 없다.

**결정** — `avg_cost`가 아니라 `total_cost`(총매입금액)를 저장한다. 평균단가는 조회 시
`total_cost / quantity`로 계산한다.

**근거** — 나눗셈을 저장하면 read-modify-write가 되지만, **덧셈으로 분해하면 원자적으로 만들 수
있다.**

```sql
UPDATE position
   SET quantity   = quantity   + :qty,
       total_cost = total_cost + :qty * :price
 WHERE account_id = :aid AND code = :code;
```

읽지 않으므로 경쟁이 없다. 락도 재시도도 필요 없다. **동시성 문제를 락으로 푸는 대신 자료구조
선택으로 없앤 것**이고, 이 프로젝트에서 가장 배울 가치가 있는 패턴 중 하나다.

**결과** — `quantity`가 0이 되면 `total_cost`도 정확히 0이어야 한다. 부동소수점을 썼다면 여기서
잔여물이 남아 평균단가가 무한이 된다(ADR-006이 정수를 쓰는 또 하나의 이유). DB 제약으로 못박았다.

```sql
CONSTRAINT position_zero_qty_zero_cost CHECK ((quantity = 0) = (total_cost = 0))
```

**배제한 대안** — 비관적 락으로 평균단가를 읽고 계산하기. 동작하지만 같은 종목에 체결이 몰릴 때
락 경합이 생기고, 애초에 필요 없는 락이다.

**재고 시점** — 선입선출(FIFO) 원가법을 도입해야 할 때. 이동평균법과 달리 매수 로트를 개별
추적해야 하므로 `position_lot` 테이블이 추가된다. 세금 계산이 정확해야 할 때만 필요하다.

## ADR-009

### 불변식을 애플리케이션과 DB에서 이중 방어

**맥락** — `available_cash >= 0` 같은 규칙을 어디서 검증할지. 애플리케이션 로직이면 충분하지
않은가.

**결정** — §03의 불변식 7개를 애플리케이션 로직과 DB 제약에서 **모두** 방어한다.

**근거** — 애플리케이션 검증은 코드에 버그가 있으면 뚫린다. 그리고 이 프로젝트가 다루는 버그는
바로 그 종류다 — 동시성 버그는 정상 경로 테스트를 전부 통과하면서 특정 타이밍에만 발생한다.
DB 제약은 어떤 코드 경로로 들어와도 적용되므로 마지막 방어선이 된다.

중요한 태도: **제약 위반 예외가 발생하면 그것은 장애가 아니라 버그 리포트다.** DB가 막아준
것은 데이터가 안전하다는 뜻이고, 그 스택트레이스가 동시성 버그의 위치를 알려준다. 그래서
제약을 "혹시 모르니 넣는 안전장치"가 아니라 **진단 도구**로 취급한다.

**결과** — Phase 0의 완료 조건이 "앱이 뜬다"가 아니라 "불변식이 DB 레벨에서 실제로 막힌다"가
됐다. `BaselineSchemaTest`가 INV-1·3·4·5·6·7을 각각 위반시켜 차단되는 것을 확인한다.

**배제한 대안** — 애플리케이션 검증만. 성능상 이점이 있다고 하지만, CHECK 제약의 비용은 무시할
수준이고 잃는 것이 너무 크다.

**재고 시점** — 없음.

## ADR-010

### Flyway (SQL 우선)

**결정** — Flyway. 마이그레이션은 순수 SQL로 작성한다.

**근거** — 이 프로젝트의 스키마에서 중요한 것이 CHECK 제약, 부분 인덱스, plpgsql 트리거다.
이들은 PostgreSQL 고유 기능이므로 DB 중립적 추상화가 이점을 주지 않는다. 오히려 SQL을 그대로
보는 것이 학습 목적에 맞고, `V1__baseline.sql`을 읽으면 불변식이 어떻게 방어되는지 한눈에 보인다.

**배제한 대안** — Liquibase(XML/YAML 추상화가 PostgreSQL 고유 기능 앞에서 결국 `<sql>` 태그로
탈출한다), Hibernate `ddl-auto`(운영에서 절대 쓰지 않을 것을 로컬에서 쓰면 스키마가 갈라진다).

**재고 시점** — 없음.

## ADR-011

### 이벤트 버스는 Redis Streams로 시작, Kafka는 나중

**맥락** — §06 C3의 종목별 직렬화는 "파티션 키 = 종목코드"로 구현한다. Kafka가 정석이다.

**결정** — Phase 3까지는 Redis Streams(또는 인메모리 채널)로 시작하고, 인스턴스를 2대 이상
띄우는 시점에 Kafka로 교체한다. **이벤트 발행 인터페이스는 처음부터 추상화**한다.

**근거** — 단일 인스턴스로도 C1~C6를 전부 겪는다. 예수금 이중 차감, 취소와 체결의 경쟁, 멱등성,
백프레셔는 모두 한 프로세스 안에서 발생한다. Kafka를 먼저 넣으면 브로커 운영·컨슈머 그룹·오프셋
관리라는 별개의 학습 부담이 동시성 학습 앞에 놓인다.

**결과** — Phase 3에서 종목별 직렬화를 코루틴 `Channel`(액터)로 먼저 구현한다. Kafka로 옮길 때
파티션 키가 그 역할을 대신하므로, 개념은 그대로이고 경계만 프로세스 밖으로 나간다. 개념을 먼저
이해하고 인프라를 나중에 붙이는 순서다.

**재고 시점** — 인스턴스를 2대 이상 띄울 때. 그 시점에 리밸런싱 중 이중 처리 문제가 새로
생기므로, `execution` 테이블의 `UNIQUE (order_id, seq)` 제약이 미리 준비되어 있다.

## ADR-012

### 시세는 한국투자증권 KIS Open API

**결정** — KIS Open API. 계좌를 개설한다.

**근거** — 국내 주식 실시간 체결가·호가를 무료로 WebSocket으로 제공하는 사실상 유일한
선택지다. 모의투자를 지원하므로 실제 자금 위험이 없고, 나중에 ADR-001을 재고할 때 실제 주문
경로가 이미 준비되어 있다.

**배제한 대안** — KRX 공개데이터(일봉만 제공, 실시간 없음 → 학습 목표 ①이 삭제됨),
키움 OpenAPI+(Windows COM 의존, macOS 개발 환경에서 불가).

**결과** — 두 가지 장애 시나리오가 따라온다. 접근토큰이 24시간마다 만료되고 발급 호출 자체에
rate limit이 있으므로 갱신 레이스를 다뤄야 한다(§R3). WebSocket 구독 종목 수에 제한이 있어
관심 종목 관리가 필요하다. 둘 다 배울 가치가 있는 문제다.

**API 키는 저장소에 커밋하지 않는다.** 환경변수로만 주입한다.

**재고 시점** — 미국 주식 확장 시(§13) KIS의 해외 시세를 쓸지, Polygon/Finnhub를 쓸지 재검토.

## ADR-013

### Testcontainers를 Phase 0부터, 싱글턴 컨테이너로

**결정** — Phase 0에서 Testcontainers를 세팅한다. 컨테이너는 `@Container`가 아니라 static
필드에서 한 번만 시작해 JVM 전체에서 재사용한다.

**근거**
- *Phase 0부터인 이유*: 동시성 테스트는 mock DB로 검증할 수 없다. 조건부 UPDATE의 원자성,
  UNIQUE 제약, 데드락은 실제 PostgreSQL에서만 발생한다. Phase 3에서 급하게 붙이면 그때 이미
  mock 기반 테스트가 쌓여 있어 되돌리기 어렵다.
- *싱글턴 컨테이너인 이유*: `@Container`는 테스트 클래스마다 컨테이너를 새로 띄운다. Phase 3에서
  동시성 테스트를 수백 번 반복 실행할 때(§12 — 경쟁 조건은 확률적으로 재현되므로 반복이 필수)
  이 차이가 결정적이다.

**결과** — 컨테이너 상태가 테스트 간에 공유되므로 테스트가 서로 간섭하지 않게 설계해야 한다.
`BaselineSchemaTest`는 `@Transactional` 대신 테스트마다 고유한 `user_id`를 쓴다. 제약 위반이
발생하면 Postgres가 해당 트랜잭션을 중단시켜 "위반시키고 → 다시 조회"가 한 트랜잭션 안에서
불가능하기 때문이다.

**재고 시점** — 없음.

## ADR-014

### 신용·증거금 거래는 범위에서 제외

**결정** — 현금 100%로만 거래한다. 신용융자, 증거금률, 반대매매를 구현하지 않는다.

**근거** — 증거금 거래는 도메인 복잡도를 크게 늘리지만(증거금률 산정, 담보 평가, 유지증거금
미달 시 반대매매) **동시성 측면에서 새로 배울 것이 거의 없다.** 여전히 잔고 차감과 조건부
UPDATE의 문제다. 학습 대비 비용이 나쁘다.

**결과** — `position.quantity >= 0`을 예외 없이 강제할 수 있다(INV-3). 공매도가 없으므로
음수 포지션이라는 개념 자체가 없고, 제약이 단순해진다.

**재고 시점** — 도메인 자체를 더 깊이 파고 싶어질 때. 그때는 동시성이 아니라 금융 도메인
학습이 목적이 된다.

## ADR-015

### Kotest(도메인) + JUnit 5(통합) 혼용

**결정** — `core-domain`의 단위·속성 테스트는 Kotest, Spring 통합 테스트는 JUnit 5 + AssertJ.

**근거** — Kotest의 `checkAll`(속성 기반 테스트)이 §12의 불변식 검증에 핵심적이다. 예시 몇 개가
아니라 무작위 입력 수천 건에 대해 성질이 성립하는지 확인해야 한다. 반면 Spring 통합 테스트에서는
`@DynamicPropertySource`, `TestRestTemplate` 같은 Spring Test 인프라가 JUnit 5와 가장 매끄럽게
붙는다. Kotest의 Spring 확장을 쓸 수도 있지만 설정 부담이 이점보다 크다.

**결과** — 두 러너가 공존한다. Gradle의 `useJUnitPlatform()` 하나로 둘 다 실행되므로 실제
불편은 없다.

**재고 시점** — 통합 테스트에서도 속성 기반 테스트가 필요해질 때.

## ADR-016

### 국내 주식을 먼저 완성하고 미국 주식으로 확장

**결정** — Phase 1~6은 국내(KOSPI/KOSDAQ)만. Phase 7에서 미국 주식을 붙인다.

**근거** — 두 시장을 동시에 지원하려면 통화·시간대·거래시간·가격제한·세금을 처음부터 추상화해야
하는데, **아직 무엇이 다른지 몸으로 모르는 상태에서 만든 추상화는 거의 틀린다.** 국내를 먼저
완성하면 구체적인 요구를 알고 나서 추상화할 수 있다.

**결과** — 대신 Phase 1~6에서 `KOSPI`, `KRW`, `09:00`을 코드에 박지 않는다. `Market`, `Money`,
`SessionSchedule`을 도메인 타입으로 두고 국내 구현을 첫 번째 인스턴스로 만든다.

**Phase 7은 설계의 채점표다.** 미국 주식을 붙이는 작업이 새 설정 추가로 끝나면 추상화가
옳았다는 증거이고, 코드를 뜯어야 하면 틀렸다는 증거다. 이 피드백을 받는 것이 Phase 7의 진짜
목적이다.

**재고 시점** — 없음.
