## 2. Phase 0 검증 기록 — 전부 통과

Docker Desktop 기동 후 5단계를 순서대로 확인했고, 모두 기대대로 동작했다.

| 단계 | 확인한 것 | 결과 |
| --- | --- | --- |
| ① `./gradlew check` | 불변식이 DB 레벨에서 실제로 막히는지 | ✅ 23건 통과 |
| ② `docker compose up -d` | 로컬 스택 기동 | ✅ postgres·redis 모두 healthy |
| ③ `GET /health` | 앱 기동 + 의존성 상태 | ✅ 200, `db`/`redis` 모두 UP |
| ④ `\dt`, 정합성 뷰 | Flyway V1 적용 여부 | ✅ 10개 테이블 + `flyway_schema_history`, `v_account_ledger_consistency` 조회됨 |
| ⑤ 원장 append-only | 트리거가 손으로도 막는지 | ✅ UPDATE·DELETE 모두 거부, INV-1 음수 예수금도 거부 |

⑤에서 실제로 받은 에러 — 규율이 아니라 DB가 막고 있다는 증거다.

```
ERROR:  원장은 append-only 입니다 (INV-4, 스펙 §05). UPDATE 연산은 허용되지 않습니다.
ERROR:  원장은 append-only 입니다 (INV-4, 스펙 §05). DELETE 연산은 허용되지 않습니다.
ERROR:  new row for relation "account" violates check constraint "account_available_cash_check"
```

정합성 뷰도 데이터를 넣은 상태에서 `drift = 0`을 확인했다. 검증용으로 넣은 행은
`TRUNCATE`로 정리해 DB는 비어 있는 상태다.

### ⚠️ 검증 중 발견한 구멍 — `TRUNCATE`는 append-only를 통과한다

`ledger_append_only` 트리거는 `BEFORE UPDATE OR DELETE ... FOR EACH ROW`라서
**`TRUNCATE`에는 걸리지 않는다.** 위 ⑤ 정리 작업에서 원장 행이 그대로 지워진 것이
그 증거다. 운영에서 원장이 통째로 날아가는 경로가 열려 있다는 뜻이므로, 다음 중
하나로 막아야 한다.

1. `CREATE TRIGGER ledger_no_truncate BEFORE TRUNCATE ON ledger FOR EACH STATEMENT ...`
   — 같은 함수를 재사용하면 된다 (`TG_OP`가 `TRUNCATE`로 들어온다)
2. 애플리케이션 DB 역할에서 테이블 소유권을 분리해 DDL/TRUNCATE 권한 자체를 제거

1번이 싸고 즉효지만, 소유자(superuser)는 트리거를 끄고 지울 수 있으므로 2번이
진짜 방어선이다.

**조치 완료** — 1번을 `V2__ledger_truncate_guard.sql`로 넣었고, 회귀 테스트
`INV-4 원장은 TRUNCATE 로도 지울 수 없다`를 함께 추가했다. 2번은 Phase 6 운영
준비에서 다룬다. 같이 발견한 `execution` 쪽 공백은 §4 Q7로 올렸다.

### 3.1 ✅ 완료 — 키움 앱키 발급 (사람이 직접)

> 2026-11-25 완료. 아래 절차는 재발급 시를 위해 남긴다. **실수 기록**: 처음 다운로드한
> 키는 실전투자용이었고, 모의 서버가 `8030: 투자구분(실전/모의)이 달라서 Appkey를
> 사용할수가 없습니다` 로 거부해서 알았다. 포털에서 계좌를 등록할 때 **모의투자 계좌**를
> 고르는 단계가 틀리기 쉽다. 환경이 갈리는 지점은 도메인이 아니라 **키 자체**다.

**AI 가 대신 할 수 없다.** 계좌 개설에 신분증·휴대폰 인증이, API 신청에 로그인·본인 확인이
필요하다. 발급되는 키는 본인 명의 금융 계좌에 실제로 주문을 넣을 수 있는 자격증명이다.

1. **키움증권 계좌 개설** — 모바일 앱에서 비대면으로. 이미 있으면 건너뛴다
2. **키움 홈페이지 ID 등록 + 계좌 연결** — API 신청이 로그인 기반이라 묶여 있어야 한다
3. **모의투자 신청** — 키움 홈페이지/영웅문 모의투자 메뉴에서 참가 신청.
   **모의투자부터 하는 것이 이 프로젝트의 결정이다** (ADR-020 → ADR-021 승계)
4. **키움 REST API 포털에서 신청** — <https://openapi.kiwoom.com>
   로그인 → `API 신청/해지` 에서 약관 동의 후 신청
5. **IP 등록** — `계좌 App Key 관리` 에서 사용할 IP 를 등록한다. **등록된 IP 에서만 인증이
   된다.** 집/사무실이 다르면 둘 다 등록하고, IP 가 바뀌면 포털에서 갱신해야 한다
6. **계좌 등록 + App Key·Secret 다운로드** — 모의투자 계좌를 등록하고 키를 내려받는다.
   **다운로드는 1 회만 가능하고 이후 비활성화된다** — 받자마자 `.env` 에 넣는다
7. `cp .env.example .env` 후 `KIWOOM_APP_KEY`, `KIWOOM_APP_SECRET`, `KIWOOM_ACCOUNT_NO` 를 채운다

> **실전과 모의는 키가 완전히 별개다.** 앱키·앱시크릿·도메인이 전부 다르고, 섞어 쓰면 인증
> 오류가 난다. `.env.example` 의 `KIWOOM_BASE_URL` 기본값은 모의투자
> (`mockapi.kiwoom.com`)로 두었다 (ADR-021).

> **키를 채팅에 붙여넣을 필요 없다.** `.env` 에 직접 넣으면 된다. `.env` 는 `.gitignore` 와
> pre-commit 훅으로 이중 차단되며 실제로 차단되는 것을 확인했다 (ADR-019). 훅의 탐지 패턴은
> `KIWOOM_*` 으로 갱신해 두었다.

### 3.2 키를 받은 뒤 — 키움 REST 클라이언트

`market-data` 모듈에 붙인다. **접근토큰 발급과 캐시부터** 시작한다.

**실측 완료 (2026-11-25, 모의 서버)**
- 토큰: `POST /oauth2/token` (client_credentials) → `return_code: 0`, `token`(86자),
  `expires_dt` = **발급 시점 + 24시간**. KIS 와 동일한 24시간 만료다 — §R3 전제 유지
- 시세: `POST /api/dostk/stkinfo` + 헤더 `api-id: ka10001` 로 삼성전자 조회 성공
- **함정 발견 — 가격 필드에 부호가 붙는다.** `cur_prc` 가 `-166900` 처럼 오는데, 이 음수는
  가격이 아니라 **전일 대비 하락 방향 표시**다. 파싱할 때 절대값을 취하고 방향은 별도
  필드(`flu_rt` 등)에서 읽어야 한다. 모르고 `toLong()` 하면 음수 가격이 DB 에 들어간다 —
  클라이언트 구현 시 이 변환을 한 곳에서 책임지게 한다

여기서 §R3(토큰 갱신 레이스)을 바로 만난다 — 만료 직후 여러 요청이 동시에 갱신을 시도하면
발급 API 가 막힌다. **Redis 분산락으로 결정했다 (2026-11-25).** 토큰 캐시도 같은 Redis 에
둔다 — 락과 캐시가 같은 곳에 있어야 인스턴스를 늘려도 일관성이 유지된다. 구현은 Redisson
같은 라이브러리가 아니라 **직접 구현**(`SET NX PX` + 소유자 토큰 + Lua 해제) 방향 — 락
만료·해제 레이스가 이 프로젝트가 배우려는 내용 그 자체라서다. 구현하면서 ADR 로 남긴다.

검증은 하네스 V5 로 — 코루틴 50개가 동시에 만료 토큰을 요구할 때 WireMock 에 발급 호출이
**정확히 1회**만 도착해야 한다.

**레이트 리미터도 여기서 필요해진다.** 모의투자는 REST 호출 제한이 **계좌(토큰)별 TR 1 개당
초당 1 회** 수준으로 빡빡해서, 종목마스터 동기화 배치가 아무 대책 없이 돌면 바로 막힌다.
이건 버그가 아니라 설계 과제다 — 스펙 §R 에 항목을 추가하고 다룬다 (ADR-021).

### 3.3 남은 작업

3. **종목마스터 동기화 배치** — `INSERT ... ON CONFLICT DO UPDATE` 로 멱등성 확보.
   **`name_chosung` 을 반드시 `Chosung.of(name)` 으로 채운다** — 컬럼이 `NOT NULL` 이라
   빠뜨리면 INSERT 가 실패한다. 조용히 누락되지 않게 일부러 그렇게 만들었다 (ADR-017)
4. **초성 검색 조회 API** — 저장값과 **검색어 둘 다** `Chosung.of()` 를 지나야 한다.
   한쪽만 정규화하면 `lg전자` 같은 입력이 조용히 안 맞는다.
   접두 일치로 할지 부분 일치로 할지는 여기서 정한다 — 접두는 `varchar_pattern_ops` 인덱스를
   타고(V3 에서 생성함), 부분 일치는 `pg_trgm` GIN 인덱스가 따로 필요하다
5. **일봉 수집** — **`is_adjusted` 값을 반드시 채운다.** 수정주가 여부를 모르고 저장하면
   §01 함정 1에 그대로 걸린다. 액면분할 종목의 과거 수익률이 조용히 망가진다
6. **조회 API 2개** — `GET /instruments?q=`, `GET /instruments/{code}/candles`

**주의** — 호가단위·거래세 값은 스펙 §01.2에 참고용으로만 적혀 있다. Phase 1에서 KRX 공식
자료로 검증하고 설정 파일 또는 DB 테이블로 넣는다. 코드에 상수로 박지 않는다.

미결정
- **Q3 장외 시간 주문** — 예약 접수 후 개장 시 처리 / 즉시 거부. *Phase 3에서 결정*
- **Q4 인증** — 자체 JWT / OAuth. *Phase 3에서 계좌를 사용자와 묶을 때 결정*
- **Q5 프론트엔드** — 없음(SSE 테스트 페이지) / React. *Phase 2에서 SSE를 눈으로 봐야 할 때 결정*
- **Q6 이벤트 버스** → Redis Streams로 시작 (ADR-011). Kafka 전환은 인스턴스 2대 이상 띄울 때
- **Q7 체결(`execution`)도 불변으로 못박을 것인가** — Phase 0 검증 중 `execution`에는
  append-only 트리거가 *아예* 없다는 것을 발견했다. 체결은 원장만큼이나 되돌릴 수 없는
  사실의 기록이고 INV-2 재구성의 근거 자료이므로 막는 쪽이 맞아 보이지만, 이건 버그
  수정이 아니라 설계 결정이다. 부분체결 정정/취소를 어떻게 표현할지(새 행 vs. 수정)와
  함께 결정해야 한다. *Phase 3에서 주문 상태 머신을 구현할 때 ADR로 결정*
- **Q8 웹소켓 제약이 실제로 무엇인가** — 키움 전환(ADR-021)으로 절반은 풀렸다: 세션당
  실시간 시세 **200 종목은 공식 문서에 있다.** 남은 미지수는 **앱키당 동시 세션 수**다 —
  1 개뿐이라면 인스턴스를 여러 대 띄울 수 없어 ADR-011(Kafka 전환) 전제와 충돌한다.
  **추정을 설계 전제로 삼지 않고 직접 측정한다.** *Phase 2에서 실측 후 ADR-021 에 기록*
