## 0. 목적과 설계 전제

### 0.1 이 프로젝트가 하려는 것

주식 거래 시스템을 **실서비스 수준으로** 만들면서, 그 과정에서 마주치는 어려운 문제들을
우회하지 않고 직접 해결한다. 산출물은 코드이지만 목표는 지식이다.

우회하지 않을 문제 네 가지:

1. **실시간성** — 초당 수천 건의 시세를 받아 화면까지 500ms 안에 전달
2. **동시성** — 같은 계좌·같은 종목에 동시 요청이 쏟아질 때 돈이 새지 않게
3. **장애** — 외부 시세 API가 죽어도, DB가 재시작해도 서비스가 무너지지 않게
4. **알림** — 유실 없이, 중복 없이, 폭발하지 않게

### 0.2 핵심 설계 분기: "구매"를 누가 체결하는가

| | **A. 자체 체결 엔진** | B. 증권사 주문 API 프록시 |
| --- | --- | --- |
| 체결 판정 주체 | 우리 서버 | 증권사 서버 |
| 동시성 학습 | 높음 (잔고·오더북 소유) | 낮음 (외부 위임) |
| 외부 장애 학습 | 중간 | 높음 |
| 계좌 개설 | 불필요 | 필요 |

**결정: A를 채택한다. 단 시세는 외부(증권사 API)에서 실시간으로 받는다.**

근거: 동시성 문제는 잔고와 주문 상태를 우리가 소유할 때만 발생한다. B를 택하면 이 프로젝트의
가장 중요한 학습 목표가 사라진다. 반면 외부 장애 대응은 시세 파이프라인만으로도 충분히 겪는다
(§7). 두 목표를 모두 달성하는 조합이다.

### 0.3 범위

**포함**
- 국내 주식(KOSPI/KOSDAQ) 현물 매수·매도
- 가상 계좌 · 예수금 · 보유 포지션 · 원장
- 실시간 시세 수집 및 클라이언트 푸시
- 자체 체결 엔진 (지정가/시장가)
- 체결 알림 및 목표가 알림

**제외 (의도적으로)**
- 신용/증거금 거래 — 현금 100%로 단순화. 증거금률·반대매매는 도메인 복잡도만 늘리고
  동시성 학습에는 새로 배울 게 없다.
- 파생상품(선물·옵션), ETF의 LP 호가 특성
- 실제 자금 이동 및 금융 규제 준수 (실서비스가 아니므로)

**2단계 확장**: 미국 주식 (§13)

## 1. 도메인 용어집

이 프로젝트를 시작하는 시점에 도메인 지식이 없다는 전제로 작성한다. 코드의 클래스명은
이 표의 영문 용어를 그대로 쓴다.

| 한글 | 영문 | 뜻 |
| --- | --- | --- |
| 종목 | Instrument | 거래 대상 하나. 삼성전자, SK하이닉스 등 |
| 종목코드 | Code / Ticker | 국내는 숫자 6자리 (`005930` = 삼성전자) |
| 시가/고가/저가/종가/거래량 | OHLCV | 특정 기간의 가격 요약. 봉(candle) 하나 |
| 호가 | Quote / Orderbook | 지금 대기 중인 매수·매도 주문의 가격별 물량 |
| 매수호가 | Bid | 사겠다는 쪽. 최우선 매수호가 = 가장 높은 매수 가격 |
| 매도호가 | Ask | 팔겠다는 쪽. 최우선 매도호가 = 가장 낮은 매도 가격 |
| 호가단위 | Tick Size | 가격을 올릴 수 있는 최소 단위. 가격대별로 다름 (§1.2) |
| 체결 | Execution / Fill | 매수와 매도가 만나 거래가 성립한 것 |
| 부분체결 | Partial Fill | 100주 주문 중 30주만 체결된 상태 |
| 미체결 | Open Order | 아직 체결되지 않고 대기 중인 주문 |
| 지정가 | Limit Order | "70,000원 이하면 산다" — 가격을 지정 |
| 시장가 | Market Order | "가격 상관없이 지금 산다" |
| 예수금 | Cash Balance | 계좌에 들어있는 현금 |
| 보유 포지션 | Position | 종목별 보유 수량 + 평균단가 |
| 평균단가 | Average Cost | 여러 번 나눠 산 경우의 평균 매입가 |
| 동시호가 | Call Auction | 장 시작·마감 직전, 주문만 받고 한 가격에 몰아서 체결하는 시간 |
| 상한가/하한가 | Price Limit | 하루에 움직일 수 있는 최대폭. 국내는 전일 종가 ±30% |
| 수정주가 | Adjusted Price | 액면분할·배당 등을 반영해 보정한 과거 주가 |

### 1.1 도메인 함정 세 가지

**함정 1 — 수정주가.** 삼성전자는 2018년 50:1 액면분할을 했다. 보정하지 않은 과거 주가를
쓰면 하루 만에 주가가 -98% 폭락한 것으로 보인다. 과거 시세를 저장할 때 원본가와 수정가를
**둘 다** 보관하고, 어느 쪽인지 컬럼으로 명시한다.

**함정 2 — `Double`로 돈을 다루기.** `0.1 + 0.2 != 0.3`이다. 국내 주식은 원 단위 정수이므로
`Long`(원)으로 충분하지만, 미장 확장 시 소수점이 등장한다. 처음부터 `Money` 값 객체로
감싸고 내부는 `BigDecimal`(scale 고정) 또는 최소단위 정수로 둔다. 원시 타입을 도메인
경계에 노출하지 않는다.

**함정 3 — `LocalDateTime.now()` 직접 호출.** 장 운영 시간 판정, 주문 유효기간, 캔들 집계가
모두 시간에 의존한다. 시간을 직접 읽으면 "장 마감 1초 전 주문" 같은 케이스를 테스트할 수 없다.
`java.time.Clock`을 주입하고 테스트에서는 `Clock.fixed()`로 교체한다. 이건 예외 없는 규칙으로
둔다.

### 1.2 규정 값 (외부 설정으로 분리할 것)

아래 값들은 금융당국·거래소 정책에 따라 **바뀐다**. 코드에 상수로 박지 말고 설정 또는 DB
테이블로 빼고, 구현 시점에 KRX 공식 자료로 검증한다. 이 문서의 숫자는 참고용이다.

**호가단위 (KOSPI 기준, 2023년 개편 후 · 검증 필요)**

| 가격 구간 | 호가단위 |
| --- | --- |
| 2,000원 미만 | 1원 |
| 2,000 ~ 5,000원 | 5원 |
| 5,000 ~ 20,000원 | 10원 |
| 20,000 ~ 50,000원 | 50원 |
| 50,000 ~ 200,000원 | 100원 |
| 200,000 ~ 500,000원 | 500원 |
| 500,000원 이상 | 1,000원 |

호가단위에 맞지 않는 가격의 주문은 **거부**한다. 이게 주문 검증의 첫 번째 규칙이다.

**거래비용 (검증 필요)**
- 매수: 위탁수수료만 (증권사별, 0.015% 내외)
- 매도: 위탁수수료 + 증권거래세 (0.18% 수준, 시장·연도별로 다름)

수수료를 반영하지 않으면 수익률이 실제보다 좋게 나온다. 체결 시점에 원장에 별도 항목으로
기록한다.

## 2. 기능 요구사항

각 항목의 완료 조건(AC, Acceptance Criteria)을 함께 적는다. AC가 없는 요구사항은
요구사항이 아니다.

### F1. 종목 (Instrument)

- F1.1 종목마스터를 외부에서 동기화한다 (코드, 종목명, 시장구분, 상장일, 액면가)
- F1.2 종목 검색: 종목코드 완전일치, 종목명 부분일치, 초성 검색(`ㅅㅅㅈㅈ` → 삼성전자)
- F1.3 상장폐지 종목은 삭제하지 않고 `delisted_at`을 채운다. 과거 주문 내역이 참조하므로.

> **AC**: 동기화를 두 번 연달아 실행해도 종목 수가 늘지 않는다 (멱등성).

### F2. 시세 (Market Data)

- F2.1 실시간 체결가를 WebSocket으로 수신한다
- F2.2 실시간 호가(10단계)를 수신한다
- F2.3 현재가 스냅샷 조회 API — 캐시에서 응답, 없으면 외부 조회 후 캐시
- F2.4 일봉/분봉 조회 API — 기간 지정
- F2.5 클라이언트에 실시간 푸시 (SSE) — 관심 종목 여러 개 구독
- F2.6 응답에는 항상 `asOf`(시세 시각)와 `stale`(신선도) 플래그를 포함한다

> **AC**: 외부 시세 소스를 강제로 종료해도 F2.3은 200으로 응답하고 `stale: true`를 반환한다.
> **AC**: 시세 수신 → SSE 도달까지 p99 < 500ms.

### F3. 계좌 (Account)

- F3.1 사용자당 가상 계좌 1개, 초기 시드머니 지급
- F3.2 예수금은 `available`(주문 가능)과 `reserved`(주문에 묶인 금액)로 분리 관리
- F3.3 보유 포지션 조회: 종목별 수량, 평균단가, 현재가 기준 평가금액, 미실현 손익
- F3.4 모든 금액 변동은 원장(ledger)에 한 줄씩 append된다

> **AC**: `available + reserved`가 원장 합계와 항상 일치한다. 불일치 시 알람.

### F4. 주문 (Order)

- F4.1 지정가 매수·매도 접수
- F4.2 시장가 매수·매도 접수
- F4.3 주문 검증: 호가단위, 상하한가, 최소 수량, 예수금/보유수량 충분성, 장 운영 시간
- F4.4 주문 취소 (미체결 또는 부분체결 잔량에 대해)
- F4.5 미체결 주문 목록 조회, 주문 내역 조회 (기간·종목 필터)
- F4.6 `Idempotency-Key` 헤더 필수 — 같은 키로 재요청하면 최초 결과를 그대로 반환

> **AC**: 같은 `Idempotency-Key`로 100개 동시 요청 → 주문은 정확히 1건 생성.
> **AC**: 예수금 100만원 계좌에 90만원 주문 2건 동시 요청 → 정확히 1건 성공, 1건 잔고부족 거부.

### F5. 체결 엔진 (Matching Engine)

- F5.1 종목별 오더북을 유지한다 (가격-시간 우선 원칙, price-time priority)
- F5.2 신규 주문이 반대편 호가와 겹치면 즉시 체결한다
- F5.3 부분체결을 지원한다
- F5.4 체결 시 예수금·포지션·원장을 하나의 트랜잭션으로 갱신한다
- F5.5 재시작 시 DB의 미체결 주문으로 오더북을 재구성한다

> **AC**: 엔진 프로세스를 kill -9 하고 재시작해도 미체결 주문이 유실되지 않는다.

### F6. 알림 (Notification)

- F6.1 체결 알림 (전량/부분)
- F6.2 목표가 도달 알림 — 사용자가 종목·가격·방향을 등록
- F6.3 채널: 텔레그램 → 웹 푸시 → 이메일 (우선순위 순)
- F6.4 발송은 at-least-once. 수신 측 중복 제거를 위해 `dedupKey`를 포함한다
- F6.5 목표가 알림은 1회 발동 후 비활성화 (또는 쿨다운)

> **AC**: 알림 채널을 죽인 상태로 체결 100건 발생 → 채널 복구 후 100건 모두 발송, 중복 없음.

### F7. 장 운영 (Market Session)

- F7.1 거래일 캘린더를 DB로 관리한다 (휴장일 포함). 하드코딩 금지
- F7.2 세션 상태: `PRE_AUCTION` / `REGULAR` / `CLOSING_AUCTION` / `CLOSED`
- F7.3 장외 시간 주문 처리 정책을 명시한다 → **§14 열린 질문**

## 3. 비기능 요구사항

### 3.1 불변식 (Invariants) — 이 프로젝트의 척추

깨지면 돈이 새는 조건들이다. **테스트로 고정하고, 부하 테스트와 카오스 테스트에서 계속
검증하고, 런타임에도 감시한다.** 다른 어떤 요구사항보다 우선한다.

| ID | 불변식 | 방어 계층 |
| --- | --- | --- |
| INV-1 | `available_cash >= 0` | DB `CHECK` + 조건부 UPDATE |
| INV-2 | `available_cash + reserved_cash = 원장 합계` | 정합성 배치 + 알람 |
| INV-3 | `position.quantity >= 0` | DB `CHECK` + 조건부 UPDATE |
| INV-4 | 모든 금액 변동 ↔ 원장 1행 (1:1) | 같은 트랜잭션 내 기록 |
| INV-5 | `filled_quantity <= quantity` | DB `CHECK` |
| INV-6 | 같은 `(account_id, idempotency_key)`로 주문 2건 불가 | DB `UNIQUE` 인덱스 |
| INV-7 | 주문 상태 전이는 상태 머신이 허용한 경로만 | 조건부 UPDATE + affected rows 확인 |

**핵심 원칙**: 각 불변식은 애플리케이션 로직뿐 아니라 **DB 제약으로도** 방어한다.
애플리케이션 코드에 버그가 있어도 DB가 마지막 방어선이 되어야 한다. 제약 위반 예외가
발생하면 그건 버그 리포트다.

### 3.2 SLO

| 지표 | 목표 |
| --- | --- |
| 시세 end-to-end 지연 (수신→SSE 도달) | p99 < 500ms |
| 주문 접수 응답 | p99 < 200ms |
| 조회 API 가용성 | 99.9% (시세 소스 장애 시 stale 응답으로 유지) |
| 주문 API 가용성 | 99% (DB 장애 시에는 정직하게 거부) |

**주문은 가용성보다 정합성이 우선이다.** 확신할 수 없으면 거부한다. 나중에 처리하겠다고
큐에 넣는 것은 금물이다 — 그 사이 가격이 변한다.

### 3.3 관측성

- 구조화 로그(JSON)에 `traceId`, `accountId`, `orderId`를 항상 포함
- 주문 접수 → 체결 → 알림을 하나의 트레이스로 연결 (OpenTelemetry)
- 불변식 위반은 최고 우선순위 알람

## 4. 아키텍처

### 4.1 모듈 구조

Gradle 멀티모듈 **모듈러 모놀리스**로 시작한다. 처음부터 마이크로서비스로 쪼개지 않는다 —
분산 트랜잭션 문제가 동시성 학습을 방해하고, 아직 경계가 어디인지 모른다.

```
stockStudy/
├── core-domain/      순수 Kotlin. Spring·JPA 의존 0.
│                     주문 상태머신, 체결 규칙, Money, 호가단위 계산
├── core-support/     공통 에러 코드, Clock 추상화, ID 생성기
├── market-data/      시세 수집(WS 클라이언트)·집계·캐시
├── trading/          계좌·주문·체결 엔진·원장
├── notification/     알림 Outbox·발송 채널 어댑터
└── api-gateway/      REST + SSE, 인증, 요청 검증
```

**`core-domain`이 프레임워크를 모르는 이유**는 미학이 아니라 실용이다. 체결 로직이 순수 함수면
DB도 Spring 컨텍스트도 없이 초당 수만 번 실행할 수 있다. 동시성 시나리오를 **속성 기반
테스트(property-based test)** 로 무작위 생성해 돌릴 수 있게 되고, 그게 이 프로젝트에서
불변식을 실제로 검증하는 유일하게 현실적인 방법이다.

### 4.2 인프라

| 컴포넌트 | 용도 | 대안/비고 |
| --- | --- | --- |
| PostgreSQL 16 | 주문·계좌·원장·종목 (트랜잭션 필수) | 시계열이 커지면 TimescaleDB |
| Redis 7 | 최신가 캐시, 분산락, Pub/Sub 팬아웃 | |
| Kafka | 도메인 이벤트, **파티션 키 = 종목코드** | Phase 3까지는 Redis Streams로 시작 가능 |
| Docker Compose | 로컬 전체 스택 | Phase 0의 완료 조건 |

Kafka를 뒤로 미루는 이유: Phase 3(체결 엔진)까지는 단일 인스턴스로도 동시성 문제를 다
겪는다. 분산 처리는 그다음 문제다. 다만 **이벤트 발행 인터페이스는 처음부터 추상화**해서
교체 가능하게 둔다.

## 6. 동시성 설계

이 프로젝트의 중심. 각 문제마다 **왜 터지는지 · 어떻게 막는지 · 왜 다른 방법은 부족한지 ·
어떻게 검증하는지**를 적는다.

### C1. 예수금 이중 차감 (Lost Update)

**시나리오**: 예수금 100만원. 90만원 주문 2건이 동시에 들어온다.

**나이브한 코드가 왜 터지는가**
```
스레드A: SELECT available → 1,000,000
스레드B: SELECT available → 1,000,000   ← 아직 A가 UPDATE 안 함
스레드A: 1,000,000 >= 900,000 ✓ → UPDATE available = 100,000
스레드B: 1,000,000 >= 900,000 ✓ → UPDATE available = 100,000
결과: 180만원을 쓰고 잔고는 10만원. 80만원이 공짜로 생겼다.
```

read-modify-write 사이의 틈이 원인이다. 검증과 차감이 원자적이지 않다.

**채택: 조건부 원자적 UPDATE**
```sql
UPDATE account
   SET available_cash = available_cash - :amount,
       reserved_cash  = reserved_cash  + :amount
 WHERE id = :accountId
   AND available_cash >= :amount;
-- affected rows == 0  →  잔고 부족. 주문 거부.
```

검증(`AND available_cash >= :amount`)과 차감이 **DB의 단일 원자 연산 안에** 들어있다.
읽고 판단하는 단계가 없으므로 틈이 없다. 왕복 1회, 명시적 락 없음, 가장 빠르다.
`affected rows`를 반드시 확인하는 것이 핵심이다 — 0이면 실패로 처리한다.

**검토했으나 채택하지 않은 방법**

- **비관적 락 (`SELECT ... FOR UPDATE`)** — 동작하지만 왕복 2회이고, 여러 행을 락할 때
  데드락 위험이 있다. 다만 계좌와 포지션을 한 트랜잭션에서 함께 봐야 하는 경우(매도)에는
  필요하다. 그때는 **항상 같은 순서로 락을 획득**한다 (예: account → position, 종목코드 오름차순).
  순서가 엇갈리면 데드락이 난다.
- **낙관적 락 (`@Version`)** — 충돌이 드물 때 좋다. 그런데 같은 계좌의 연속 클릭("따닥")은
  충돌이 잦은 케이스다. 재시도 폭풍이 일어난다.

**검증**: 예수금 100만원 계좌에 90만원 주문을 스레드 200개로 동시 발사 → 성공 1건, 거부
199건, 최종 잔고 10만원. `available_cash`가 한 번도 음수가 되지 않음.

### C2. 취소와 체결의 경쟁 (Race on State Transition)

**시나리오**: 사용자가 취소 버튼을 누른 순간, 체결 엔진이 그 주문을 체결하고 있다.

**나이브한 코드**
```kotlin
val order = repo.findById(id)              // status = ACCEPTED
if (order.status == ACCEPTED) {             // ← 이 틈에 엔진이 FILLED로 바꿈
    order.status = CANCELLED                //   덮어쓴다
    repo.save(order)
}
// 결과: 체결됐는데 상태는 CANCELLED. 포지션은 늘었고 주문은 취소됨. 정합성 붕괴.
```

**채택: 조건부 상태 전이 + affected rows 확인**
```sql
UPDATE orders
   SET status = 'CANCELLED', updated_at = now()
 WHERE id = :orderId
   AND status IN ('ACCEPTED', 'PARTIALLY_FILLED');
-- affected == 0  →  이미 체결됐거나 이미 취소됨.  HTTP 409 Conflict 반환.
```

**규칙: 주문 상태는 절대 read-then-write 하지 않는다.** 모든 전이는 현재 상태를 `WHERE`에
담은 단일 UPDATE로 하고, `affected rows`로 성공을 판정한다. §5.1 상태 머신의 각 화살표가
하나의 조건부 UPDATE에 대응한다.

부분체결 취소는 잔량만 취소한다 — `quantity - filled_quantity`만큼의 예약을 해제하고
상태를 `CANCELLED`로 바꾸며, 이미 체결된 부분은 그대로 유지한다.

**검증**: 같은 주문에 대해 취소 요청과 체결 처리를 동시 실행 → 정확히 하나만 성공하고,
포지션과 원장이 성공한 쪽과 일치.

### C3. 체결 엔진의 단일 소유권

**문제**: 오더북은 "가격-시간 우선"으로 정렬된 자료구조다. 두 인스턴스가 같은 종목의
오더북을 동시에 만지면 순서가 깨지고, 같은 물량이 두 번 체결될 수 있다.

**채택: 종목 단위 직렬화(serialization by instrument)**

핵심 통찰: **오더북은 종목마다 완전히 독립적이다.** 삼성전자 체결과 SK하이닉스 체결 사이에는
아무 관계가 없다. 그래서 전체를 직렬화할 필요 없이 종목별로만 직렬화하면 된다.

- Kafka **파티션 키 = 종목코드** → 같은 종목의 주문은 항상 같은 파티션 → 항상 같은 컨슈머
- 한 컨슈머 프로세스 안에서는 종목별 단일 처리 흐름
  (코루틴 `Channel` 하나 = 액터 하나, 또는 종목코드 해시로 스레드 고정)
- 인스턴스를 늘리면 파티션이 나뉘어 각자 다른 종목을 담당한다 → **종목 수만큼 수평 확장 가능**

**리밸런싱 중 이중 처리**: 컨슈머가 추가·제거되면 파티션 소유권이 이동하는데, 그 순간
같은 메시지를 두 인스턴스가 처리할 수 있다. 그래서 체결 처리 자체가 멱등이어야 한다 —
`execution` 테이블에 `(buy_order_id, sell_order_id, seq)` UNIQUE를 두고, 중복 insert는
무시한다.

**오더북 복구**: 오더북을 메모리에만 두면 프로세스 사망 시 미체결 주문이 사라진다.
주문은 항상 DB에 먼저 쓰고(`INDEX (code, status)`), 시작 시 미체결 주문을 읽어 오더북을
재구성한다. 메모리 오더북은 DB의 파생 캐시다.

**검증**: 체결 엔진을 `kill -9` → 재시작 → 오더북이 DB 상태와 동일하게 복구.

### C4. 중복 요청 (따닥)

**문제**: 사용자가 매수 버튼을 두 번 누른다. 또는 클라이언트가 타임아웃 후 재시도한다.
네트워크가 불안하면 서버는 이미 처리했는데 클라이언트만 실패로 아는 경우가 생긴다.

**채택: Idempotency-Key**

- 클라이언트가 주문마다 UUID를 생성해 `Idempotency-Key` 헤더로 보낸다
- 서버는 `UNIQUE (account_id, idempotency_key)`로 중복을 **DB가** 막는다 (INV-6)
- 중복 키 예외가 나면 → 기존 주문을 조회해 **최초 결과를 그대로 반환**한다 (에러가 아니다)

애플리케이션에서 `SELECT`로 먼저 확인하는 것은 C1과 같은 이유로 안 된다. UNIQUE 제약이
유일하게 신뢰할 수 있는 중복 방어다. "먼저 조회하고 없으면 insert"는 동시 요청에서 깨진다.

**검증**: 같은 키로 200개 동시 요청 → 주문 1건, 응답 200개 모두 동일한 order_id.

### C5. 시세 폭주와 백프레셔

**문제**: 장 시작 직후 삼성전자 하나만으로도 초당 수백 건의 체결 tick이 온다. 전 종목이면
초당 수만 건이다. 이걸 그대로 DB에 넣거나 그대로 클라이언트에 밀면 죽는다.

**채택: 컨플레이션(conflation) + 계층별 다른 속도**

핵심 통찰: **모든 tick이 모든 소비자에게 필요하지는 않다.** 소비자마다 필요한 해상도가 다르다.

| 소비자 | 필요한 것 | 처리 |
| --- | --- | --- |
| 화면의 현재가 | 최신값만 | Redis `SET` (덮어쓰기가 곧 컨플레이션) |
| SSE 푸시 | 사람이 인지할 수 있는 주기 | 100ms 타이머로 스냅샷 전송 |
| 차트/분석 | 1분 단위 집계 | 메모리 집계 → 1분마다 배치 insert |
| 체결 엔진 | 가격 변화 이벤트 | 가격이 실제로 바뀐 tick만 |

Redis에 최신값을 덮어쓰는 것 자체가 자연스러운 컨플레이션이다. 초당 300건이 와도 Redis에는
최신 1건만 남고, 100ms마다 읽어 보내면 초당 10건만 나간다. 30배 감소인데 사용자는 차이를
느끼지 못한다.

**백프레셔**: 어떤 큐도 unbounded로 두지 않는다. 소비자가 생산자보다 느리면 무한 큐는
반드시 OOM으로 끝난다.
```kotlin
Channel<Tick>(capacity = 1024, onBufferOverflow = BufferOverflow.DROP_OLDEST)
```
시세는 **최신값이 중요하고 과거값은 버려도 되는** 데이터이므로 `DROP_OLDEST`가 옳다.
드롭이 발생하면 메트릭으로 기록한다 — 조용히 버리면 안 된다.

**주의**: 이 판단은 시세에만 적용된다. **주문과 체결은 절대 드롭하지 않는다.** 그쪽 큐가
차면 접수를 거부(429)하는 것이 옳다.

### C6. 평균단가 갱신 경쟁

**문제**: 평균단가는 `(기존수량×기존단가 + 체결수량×체결가) / (기존수량+체결수량)`이다.
기존 값을 읽어야 계산할 수 있으므로 read-modify-write가 불가피하다. C1의 조건부 UPDATE
트릭을 그대로 쓸 수 없다.

**채택: 총매입금액을 저장한다**

평균단가 대신 `total_cost`(총 매입금액)를 저장하면 덧셈만으로 갱신할 수 있고, 평균단가는
조회 시 `total_cost / quantity`로 계산한다.
```sql
UPDATE position
   SET quantity   = quantity   + :qty,
       total_cost = total_cost + :qty * :price
 WHERE account_id = :aid AND code = :code;
```
읽지 않으므로 경쟁이 없다. 나눗셈을 저장하면 read-modify-write가 되지만, 덧셈으로 분해하면
원자적으로 만들 수 있다 — 동시성 문제를 자료구조 선택으로 없애는 예다.

매도 시에는 평균단가를 바꾸지 않고 수량과 총매입금액을 비례 감소시킨다(이동평균법). 실현손익은
`(매도가 - 평균단가) × 수량 - 수수료 - 세금`으로 원장에 기록한다.

> **참고**: `quantity`가 0이 되면 `total_cost`도 0이어야 한다. 부동소수점을 쓰면 여기서
> 잔여물이 남는다. 정수 산술을 쓰는 또 하나의 이유다.

## 7. 장애 대응

### R1. 외부 시세 API 장애

**대응**: Resilience4j 서킷 브레이커 + 폴백.

폴백은 Redis에 캐시된 마지막 가격을 반환하되, **응답에 `asOf`와 `stale: true`를 반드시
포함한다.** 오래된 가격을 신선한 것처럼 주는 것이 장애보다 위험하다 — 사용자가 그걸 보고
거래 판단을 한다.

`stale` 상태에서는 **시장가 주문을 거부한다.** 신뢰할 수 있는 현재가가 없으면 시장가를
체결할 수 없다.

### R2. WebSocket 연결 끊김

**대응 3단계**
1. **재연결** — 지수 백오프 + 지터(jitter). 지터가 없으면 여러 인스턴스가 동시에
   재연결을 시도해 외부 API를 다시 쓰러뜨린다(thundering herd).
2. **갭 복구** — 재연결 직후 REST 스냅샷을 호출해 끊긴 동안의 상태를 메운다. WebSocket
   재연결만으로는 놓친 구간을 알 수 없다.
3. **유실 감지** — 시퀀스 번호나 서버 타임스탬프의 단절을 메트릭으로 노출한다.
   "조용히 시세가 안 오는 상태"가 최악의 장애다. **연결 상태가 아니라 데이터 도착을
   헬스체크로 삼는다** — 연결은 살아있는데 데이터만 안 오는 경우가 실제로 있다.

### R3. 접근토큰 갱신 레이스

증권사 API 접근토큰은 보통 24시간 유효하고, **발급 호출 자체에 rate limit이 있다.**
만료 시점에 인스턴스 여러 개가 동시에 갱신을 시도하면 rate limit에 걸려 전부 실패한다.

**대응**: Redis 분산락(`SET key value NX EX 30`)을 잡은 하나만 갱신하고, 나머지는 짧게
대기한 뒤 캐시에서 읽는다. 만료 직전(예: 남은 유효시간 10%)에 선제적으로 갱신해 만료
순간의 동시 요청 자체를 피한다.

### R4. 알림 발송 실패 → Transactional Outbox

**문제**: 체결 트랜잭션을 커밋한 직후 알림을 보내려는데 텔레그램이 죽어있다. 반대로 알림을
먼저 보내고 트랜잭션이 롤백되면 "체결되지 않은 체결 알림"이 간다. 어느 순서든 깨진다.

**대응: Outbox 패턴**
1. 체결 트랜잭션 **안에서** `notification_outbox`에 행을 insert한다 (같은 트랜잭션이므로
   체결과 알림 발행이 원자적으로 함께 커밋되거나 함께 롤백된다)
2. 별도 워커가 outbox를 폴링해 발송한다
3. 실패 시 `retry_count`를 올리고 `next_retry_at`을 지수 백오프로 미룬다
4. N회 초과 시 DLQ 상태로 옮기고 알람

**at-least-once의 대가**: 발송 후 상태 갱신 직전에 워커가 죽으면 같은 알림이 두 번 간다.
피할 수 없으므로 **페이로드에 `dedupKey`를 넣어 수신 측이 중복을 제거**하게 한다.
exactly-once는 분산 시스템에서 공짜로 얻을 수 없다 — at-least-once + 멱등 수신이
현실적인 답이다.

### R5. DB 장애

- **조회**: Redis 캐시로 degraded 서비스 유지. 시세와 최근 잔고 스냅샷은 응답 가능
- **주문**: 정직하게 거부한다(503). §3.2에서 정한 원칙 — 정합성이 가용성보다 우선
- 주문을 큐에 넣어 나중에 처리하는 것은 **금물**. 몇 분 뒤의 가격은 사용자가 의도한 가격이 아니다

### R6. 체결 엔진 인스턴스 사망

C3에서 다룬 대로 오더북을 DB에서 재구성한다. 추가로 **처리 중이던 메시지**가 재처리되므로
체결 처리가 멱등해야 한다 (`execution` UNIQUE 제약).

### R7. 카오스 테스트 — 이 모든 것을 실제로 검증하기

대응책을 써두는 것과 동작하는 것은 다르다. 다음을 **자동화된 테스트로** 만든다.

| 주입할 장애 | 도구 | 확인할 것 |
| --- | --- | --- |
| 시세 소스 종료 | 컨테이너 stop | 조회 API가 stale로 응답, 시장가 주문 거부 |
| 네트워크 지연·패킷 손실 | toxiproxy | 서킷 브레이커 동작, 타임아웃 준수 |
| DB 재시작 | 컨테이너 restart | 커넥션 풀 복구, 주문 거부 후 정상화 |
| 체결 엔진 kill -9 | 프로세스 종료 | 오더북 복구, 주문 유실 0 |
| 알림 채널 종료 | 컨테이너 stop | outbox 적체 후 복구 시 전량 발송, 중복 없음 |

**모든 테스트의 공통 사후 조건: §3.1의 불변식 7개가 전부 유지된다.**

## 8. 알림 설계 — 목표가 평가의 알고리즘

체결 알림은 이벤트 기반이라 단순하다. 어려운 건 목표가 알림이다.

**나이브한 구현이 왜 안 되는가**: tick이 올 때마다 그 종목의 모든 알림 조건을 순회하면
`O(tick 수 × 조건 수)`다. 초당 수만 tick × 수만 조건 = 초당 수억 번 비교. CPU가 녹는다.

**채택: 종목별 가격 정렬 구조 + 구간 조회**

종목별로 알림 조건을 **가격순으로 정렬된 구조**(`TreeMap<Price, List<Alert>>`)에 담고,
tick이 오면 **직전 가격과 현재 가격 사이 구간에 걸린 조건만** 꺼낸다.

```
이전가 69,500 → 현재가 70,200 (상승)
  → 상향 돌파 알림 중 (69,500, 70,200] 구간의 것만 발동
  → TreeMap.subMap(69500, false, 70200, true)
```

복잡도가 `O(log n + k)`로 떨어진다 (k = 실제 발동된 알림 수). 가격이 움직이지 않은 tick은
빈 구간이므로 사실상 비용이 0이다. 상향/하향을 별도 구조로 관리한다.

**추가 규칙**
- 발동한 알림은 `active = false`로 즉시 비활성화 (또는 쿨다운 설정). 안 하면 가격이
  경계에서 진동할 때 알림이 수백 건 쏟아진다
- 알림 발동 자체는 Outbox에만 쓰고, 실제 발송은 워커에 맡긴다 (R4). 시세 처리 스레드에서
  절대 HTTP 호출을 하지 않는다 — C5의 백프레셔가 무너진다

## 9. 장 운영과 시간

- **거래일 캘린더는 DB 테이블**로 관리한다. 휴장일은 매년 바뀌고 임시 휴장도 있다
- **세션**: `PRE_AUCTION`(08:30~09:00) / `REGULAR`(09:00~15:20) /
  `CLOSING_AUCTION`(15:20~15:30) / `CLOSED` — 시간은 설정값으로, 세션 판정은 도메인 로직으로
- **시간대**: 저장·로깅은 UTC, 도메인 판정은 `Asia/Seoul`. 서버 타임존에 의존하지 않는다
- **`Clock` 주입 필수** (§1.1 함정 3). "장 마감 1초 전 주문"을 테스트할 수 없으면 그 코드는
  검증되지 않은 것이다

동시호가는 실시간 체결과 규칙이 완전히 다르다(단일가 결정). Phase 3에서는 `REGULAR`만
구현하고 동시호가는 Phase 6 이후로 미룬다 — 별도의 알고리즘이고, 먼저 배울 것이 많다.

## 13. 미국 주식 확장 시 달라지는 것

Phase 7에서 겪을 일을 미리 적어둔다. **여기 적힌 것들이 처음부터 추상화되어 있어야 한다.**

| 항목 | 국내 | 미국 | 설계 대응 |
| --- | --- | --- | --- |
| 통화 | KRW, 정수 | USD, 소수점 | `Money(amount, currency)` 값 객체 |
| 최소 거래 단위 | 1주 | 소수점 주식 가능 | 수량도 정수 가정을 하지 않는다 |
| 시간대 | Asia/Seoul, 고정 | America/New_York, **DST 있음** | 세션은 데이터로, `ZoneId`로 판정 |
| 거래 시간 | 09:00~15:30 | 정규장 + 프리/애프터마켓 | 세션을 enum이 아닌 테이블로 |
| 가격 제한 | ±30% 상하한가 | 상하한가 없음, LULD 변동성 중단 | 검증 규칙을 시장별 전략으로 |
| 거래세 | 매도 시 부과 | 없음 (대신 SEC fee 등) | 비용 계산을 시장별 정책 객체로 |
| 종목코드 | 숫자 6자리 | 알파벳 심볼 (`AAPL`) | `code`를 문자열로 (이미 그렇게 설계됨) |
| 환율 | — | 필요 | 환율 소스 추가, 평가금액 이중 표기 |

**설계 원칙**: Phase 1~6에서 `KOSPI`나 `KRW`나 `09:00`을 코드에 박지 않는다. 대신
`Market`, `Money`, `SessionSchedule`을 도메인 타입으로 두고 국내 구현을 첫 번째 인스턴스로
만든다. 미국 주식을 붙이는 작업이 **새 설정 추가**로 끝나면 추상화가 옳았다는 증거이고,
코드를 뜯어야 하면 틀렸다는 증거다. Phase 7은 설계의 채점표다.

| Q3 | 장외 시간 주문 | 예약 접수 후 개장 시 처리 / 즉시 거부 | 전자가 현실적이나 상태가 하나 늘어남 |
| Q4 | 인증 | 자체 JWT / OAuth(소셜) | 학습 초점이 아니므로 간단한 쪽 |
| Q5 | 프론트엔드 | 없음(API + SSE 테스트 페이지) / React 대시보드 | Phase 6까지는 최소 페이지로 충분 |
| Q6 | 이벤트 버스 | Kafka부터 / Redis Streams로 시작 후 교체 | Phase 3까지는 후자로도 충분 |

**Q2가 가장 중요하다.** 사용자 간 매칭만 구현하면 혼자 테스트할 때 주문이 영원히 체결되지
않는다. 외부 실시간 시세를 기준으로 체결을 판정하는 가상 상대방을 두면, 오더북과
가격-시간 우선 로직은 그대로 유지하면서 실제로 체결이 일어나는 것을 볼 수 있다.
